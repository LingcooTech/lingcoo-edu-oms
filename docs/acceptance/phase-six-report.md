# 第六阶段验收报告：教学资源与排课

日期：2026-09-08

## 结论

第六阶段已完成并在独立预览数据库、真实 API、真实管理端页面上通过验收。

本阶段建立的是“教学资源与排课上下文”，没有改变已经确定的课时核心模型：课时权益仍只属于学员在某个机构下的课时账户，课程、班级、校区、教室、教师和排课计划都不能限定课时包。

## 已实现范围

- 组织共享校区和教室管理；校区、教室不绑定某个机构。
- 机构内课程和班级管理。
- 班级当前学员名单管理，最多一次维护 500 人。
- 可复用排课计划、计划教师、周几/日期/时区规则。
- 按计划生成独立草稿课次。
- 课次资源上下文和名称快照。
- 可选复制班级当前名单，默认关闭。
- 重复生成同一计划日期时安全跳过，不重复创建课次。
- 教师和教室冲突默认整批拒绝；计划生成覆盖冲突时必须填写原因并写审计。
- 跨机构共享教师、共享教室按组织范围检查冲突。
- 冲突检查和写入使用同一事务与组织级事务锁，避免并发请求同时通过检查。
- 手工关联教师/教室时检查冲突；关联后再调整课次时间也会重新检查。
- 资源停用/归档，不提供会破坏历史引用的物理删除接口。

## 核心不变量

1. 没有课程、班级、校区、教室或教师，课次仍然可以创建和运行。
2. 计划是生成规则，不是历史课次的控制器；编辑计划不会回写已生成课次。
3. 只有显式勾选 `includeClassStudents=true` 才复制班级当前有效成员。
4. 复制后，课次名单和班级名单独立演进。
5. 资源名称以生成或关联当时的快照进入课次；以后重命名资源不会篡改历史显示。
6. 只有 `draft`、`open` 课次参与未来冲突检查；`completed`、`cancelled` 不阻止未来排课。
7. 教师和教室是组织内可共享资源，因此冲突不能按机构隔离。
8. 默认冲突策略是原子拒绝，不允许无提示的部分成功。

## 管理端入口

- `/admin/teaching-resources`：课程、班级、组织共享校区和教室。
- `/admin/schedule-plans`：排课计划、计划教师和课次生成。
- `/admin/lesson-sessions`：查看独立课次、教师、名单和资源上下文。

所有新增和编辑交互均采用 Modal，没有引入右侧 Drawer。

## 数据与接口边界

- `teaching-resources` 模块拥有校区、教室、课程、班级、计划、计划日期和课次资源上下文。
- `lesson-sessions` 模块继续拥有课次、课次教师、名单、签到和消课。
- 两个模块通过公开排课端口和资源冲突策略协作，没有直接访问对方 Repository。
- Contract、API Client、服务端路由和管理端调用均使用同一类型定义。
- 数据库迁移：`0027_needy_mad_thinker.sql`。
- 迁移画像脚本只读旧系统，不写旧库，也不自动导入数据。
