# Webhook Inbox 架构决策

- 状态：已采纳
- 日期：2026-09-03
- 决策：当前不把通用 Webhook Inbox 作为 Business Starter 默认模块

## 背景

Payments 已提供 Starter 中第一个公开 Provider 回调入口。回调处理包含精确原始 HTTP Body 验签、Provider
身份校验、金额与币种校验、事件去重、支付状态机更新、Audit 和不可变回调事实。

阶段 13 评估是否应把这些能力提取为独立 Webhook Inbox，统一接收、保存、重试和重放第三方回调。

当前证据仍限于 Starter 内的 Mock Payment Provider；尚无第二个独立回调领域，也尚未完成真实支付 Provider
项目接入。因此，原计划要求的通用化证据门槛尚未满足。

## 决策

当前保持回调由其业务所有者模块处理：

- Payments 继续拥有 `payment_callbacks`、回调路由、验签和支付状态事务；
- Provider 差异继续封装在 `PaymentProviderAdapter.verifyCallback`；
- 精确原始 Body 只用于验签和计算 SHA-256，默认不持久化；
- 验签成功后的稳定业务事实与支付状态在同一数据库事务中提交；
- 跨模块可靠发布使用 Transactional Outbox，耗时异步处理使用 Jobs；
- HTTP 客户端主动请求的结果重放继续使用 Idempotency，不与 Provider 回调去重混用。

不新增 `webhook_inbox` 表、通用公开接收端点、通用重放 API、权限或 Admin 页面。

## 原因

1. 当前只有 Payments 一个已经实现的入站回调领域，尚未形成两个独立消费者都需要的稳定抽象。
2. 签名算法、事件身份、时间窗、防重放、商户身份和响应协议都属于 Provider Contract，无法由通用表可靠推断。
3. Payments 必须在一个事务中完成回调去重、金额校验和状态变更。先写通用 Inbox 再异步消费会引入不必要的最终一致性窗口。
4. 保存原始载荷会扩大 PII、凭据和支付数据的暴露面，并要求额外定义加密、大小限制、保留期、删除和访问审计。
5. 通用“重放”可能重复触发退款、发货或通知等不可逆副作用；安全重放必须由领域状态机和幂等规则控制。
6. 通用 Admin 权限无法表达不同领域的数据可见性。支付回调继续受 `payments.read` 保护更清晰。

## 与现有基础设施的边界

| 能力                          | 所有者                | 不承担                          |
| ----------------------------- | --------------------- | ------------------------------- |
| Provider 回调验签与业务校验   | 领域 Provider Adapter | 通用 Inbox 不猜测签名或事件语义 |
| 已验证回调事实和领域状态      | Payments 等业务模块   | Outbox 不接收入站 HTTP          |
| 可靠发布已提交的内部/外部事件 | Transactional Outbox  | 不作为原始回调存储              |
| 耗时、可重试的异步命令        | Jobs                  | 不替代回调身份与领域幂等        |
| 主动 HTTP 写请求结果重放      | Idempotency           | 不处理 Provider 主动推送        |

## 重新评估门槛

只有同时满足以下条件时，才重新考虑默认 Webhook Inbox：

1. 至少两个独立业务领域或 Provider 已在真实项目中接入，并出现相同的接收生命周期需求；
2. 可证明共享模型能减少重复代码，同时不拆散领域事务；
3. 已明确每个 Provider 的最大 Body、验签时间窗、事件身份、防重放和响应时限；
4. 已决定是否保存载荷；如必须保存，需先定义 Envelope 加密、Secret 轮换、保留清理和最小权限；
5. 重试和人工重放有领域级幂等证明、审计记录和不可逆副作用保护；
6. Contracts 不暴露 Provider SDK 类型、签名密钥、原始载荷或内部错误。

达到门槛后，优先提取一个只负责安全 HTTP 接收和已验证 Envelope 交接的窄适配层；业务事实、状态机和重放决策仍由领域模块拥有。

## 结果

该决策保持 Starter 轻量，避免为了单一场景建立万能收件箱，同时保留未来从两个真实实现中提取稳定抽象的路径。阶段 14 可以继续聚焦 CLI、生成项目和发布验收。
