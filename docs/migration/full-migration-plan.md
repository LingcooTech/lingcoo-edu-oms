更新日期：2026-09-09。
状态：P1–P6 的主要工程实现、隔离数据库迁移演练及真实 Web 验收已完成；当前暂停正式数据迁移，先按旧系统逐模块完成功能核对、补齐和实际运营演练；P7 周期权益与后续正式切换待实施；未执行旧生产数据正式导入和生产切换。
本版替代本文件此前“组织内通用课时＋订单支付前置”的方案。历史验收报告不改写，旧系统原始资料不覆盖。

## 1. 目标与边界

目标是单租户自部署的运营管理系统：组织运营空间，自营及合作机构提供教学服务，系统管理人员、机构课时、课次、签到、运营记录。实际收费、退款和分账在线下完成，不要求经过系统。

已确认的核心原则：

1. 组织是技术租户，一个部署服务一个组织；不建设租户开通、租户切换、SaaS 计费或共享数据库多租户运营能力。
2. 机构是教学服务和课时提供方。自营与合作使用同一机构模型，通过类型区分；不以空机构表示自营。
3. 普通课时在机构内通用、机构间隔离，不受课程、系列、班级、老师、校区或教室限定。
4. 学员是权益持有人，按“学员＋机构”独立记账；家长绑定赋予访问及获准操作能力，不拥有或合并孩子的课时。
5. 课次是某机构的一次教学服务事件，必须明确服务机构；课程、班级、老师、场地为可选关联。无完整教学档案也可创建独立课次并签到消课。
6. 场地可以共享，场地归属不推导服务机构或扣课机构；同一教室可在不冲突时段供不同机构使用。
7. 先做好最小闭环，再逐层增加政策与配置。正确性底线不能配置关闭，经营规则可在明确需求后逐步配置。
8. 周期卡后置；订单、支付、资金退款、分成结算、财务报表不在本轮迁移实施范围。

核心验收式：

> 建立机构和学员 → 绑定家长 → 登记发放该机构课时 → 创建该机构独立课次 → 签到消课 → 查询及纠错。
> 整个链路不需要订单、支付、课程、班级、教师或校区档案。

这里“不需要教师档案”不等于无人负责：每次操作仍必须有已授权的操作账号。

可记录“线下购课登记”作为发课来源说明，但系统不判断钱是否到账、不生成收款事实、不伪造已支付订单。价格不是发课、签到或消课必填信息；金额展示若以后确有需要，应独立讨论，不恢复财务依赖。

线下退款后，系统可由授权人员登记“课时扣回”，只处理剩余权益和原因，不处理退款金额。取消线下退款也不能自动恢复课时，须另有明确权益操作。

## 3. 核心模型与约束

| 对象           | 必须表达                                                 | 明确不做                                 |
| -------------- | -------------------------------------------------------- | ---------------------------------------- |
| 组织           | 单实例租户配置、名称、品牌                               | 多租户运营平台                           |
| 机构           | 服务主体、类型、状态、员工授权关系                       | 当作单独租户；用场地或收款方替代         |
| 学员           | 组织内唯一档案、有效状态                                 | 按机构复制成多个不相干学生               |
| 学员与机构关系 | 运营归属／服务关系、建立来源、可见范围                   | 因同一组织而向所有合作机构暴露全部学员   |
| 家长与绑定     | 家长档案、账号关联、多对多绑定、状态与核实记录           | 同手机号自动认领；解绑转移课时           |
| 课时包模板     | 所属机构、名称、普通课时数、赠课数、状态、版本           | 课程限制、收款状态、必填订单或金额       |
| 发放凭证与批次 | 学员、机构、实际数量、类型、原因、模板快照、操作人和时间 | 修改历史发放量冒充续课；依赖可变商品数据 |
| 课时账户       | 学员＋机构唯一、课时余额、版本／序号                     | A 机构不足自动借用 B 机构余额            |
| 课次           | 稳定 ID、服务机构、主题／说明、时间、状态、可选教学关联  | 必须从班级生成；绑定具体课时包           |
| 签到           | 课次＋学员身份、出勤事实、操作来源、修订历史、消课状态   | 将出勤状态直接等同于固定扣课数量         |
| 消费凭证与分摊 | 学员、机构、课次、数量、实际扣减批次、当时规则与原因     | 根据后来修改的课次或模板重新推导历史     |
| 课时流水       | 发放、消费、冲正、扣回、调整及来源追溯                   | 普通 API 直接设置余额或删除历史          |

对用户展示各机构余额；组织级数量汇总只能作为统计，不能展示成“可跨机构消费的总余额”。每个机构内部可以自动跨多个批次分摊，不让用户每次手动选包。

学员是组织级档案，但机构只访问明确授权的学员及字段。机构开户、服务关系建立、机构员工检索学员的策略在 P2 固化：不得因为建立新关系而泄露其他机构课时或全组织联系方式；不得仅凭用户提交的 institutionId 获得权限。

### 3.1 必须由代码与数据库共同保证的底线

- 发放所属机构、账户机构、消费机构、课次服务机构必须一致；跨模块端口同样检查，不只依赖 HTTP。
- 模板被实际使用后，不通过修改 institutionId 转移历史权益。课次已有签到／消费后不直接换机构；更正需撤销关联事实后重建或走受控修订。
- 所有余额变动经过统一课时应用服务；余额投影与有符号流水在同一事务内更新。
- 课时余额不为负；同一账户并发发放、扣减、冲正、扣回有明确锁顺序及版本控制。
- 来源发放唯一、课次学员签到身份稳定、修订号明确。持久业务唯一约束配合请求幂等，防止不同客户端对同一事实重复记账。
- 相同幂等键、相同载荷安全重试；相同键、不同载荷返回冲突，不能静默当成功。
- 消费凭证、批次分摊、流水、签到消课结果、成功审计与 Outbox 同事务提交。
- 已入账流水不可经常规操作修改／删除；冲正引用原凭证、原分摊，返还原机构原批次，防重复返还。
- 已消费发放不能直接整笔撤销成负数；区分发放纠错、消费冲正和剩余课时扣回，拒绝无依据补平。
- 续课登记创建新批次，不覆盖旧批次，不更新班级或未来课次的默认课包。
- 删除／停用机构、模板、课程、人员和场地不级联删除历史权益；机构停用策略明确且留痕，不能顺便把余额清零。
- 零消课的签到保留业务事实，不制造零数量流水。失败日志与成功记账审计分开。
- 课时数量采用明确精度的整数存储，不用浮点直接相加扣减。
- 权限涵盖列表、详情、统计、导出、写入、后台任务及文件访问；解绑、停用、撤销员工授权及时生效。

### 3.2 课次的灵活性边界

课程／班级可以提供默认值，但不是课次创建或消费前提；默认值与历史事实不混用。

计划阶段可以受控调整时间、老师、地点和课程关联；资源已选择就检查引用与冲突，必要的管理员例外需明确权限和原因。已发生课次的服务时间、实际老师及地点等通过修订留痕，不能重写消费事实。

同一时段多个机构联合活动，第一版按服务机构拆为独立课次，可共享活动标识；不把一个扣课课次做成无法确定机构的混合事件。是否支持联合活动独立功能以后再评估。

## 4. 规则分层：先固定实现，再开放配置

| 层级           | 内容                                           | 实施方式                                         |
| -------------- | ---------------------------------------------- | ------------------------------------------------ |
| 核心底线       | 归属、非负、幂等、事务、不可随意改账、授权     | 代码与数据库约束，不允许关闭                     |
| 最小运营政策   | 每次消课数、分摊顺序、签到方式、补签／纠错权限 | 集中策略函数、明确默认值和测试，不散落 Route     |
| 后续可配置政策 | 请假缺席、取消窗口、有效期、审批、消课数量覆盖 | 按真实需求逐项配置，限定字段和作用范围，保存版本 |
| 高级自定义     | 可视化规则编排、脚本、任意表达式               | 不在当前计划中，不先造通用引擎                   |

每次消费保存实际数量及决策依据，规则改变只影响之后的业务，不自动重算历史。第一版不预置跨机构互通开关：机构隔离是当前已确认业务边界。

以下默认值为实施建议，须在对应阶段用例设计时确认，不阻塞前序模块：

- P2：机构人员可见字段与建立学员服务关系的权限；家长绑定核实方式。建议组织统一档案、机构最小可见、管理员核实绑定起步。
- P3：是否只支持整数课时；建议先整数，若需半课时须在正式入账前确定统一比例。默认同机构按发放时间与稳定 ID 顺序消费，可跨批次。
- P3：新普通课时是否无到期；建议首版不新增自动到期规则。旧有效期不能静默清除，须单独核对处理。
- P4：默认消课数量建议 1，员工明确确认，可按权限调整并留原因；家长不得任意输入扣减数。
- P4：建议支持“不消课签到”；余额不足建议保留“已到场、待处理”状态，后续授权补扣。创建该状态是明确用例，不是事务失败留下的半笔记录。
- P4：补签时间窗口、正常签到渠道、撤销权限及缺席／请假规则；不默认缺席就扣课。
- 不做透支、跨机构转课、跨学员共享，也不把周期权益折成任意大额普通课时。

## 5. 分阶段路线

> **执行顺序调整（2026-09-09）：** 原 P8 数据迁移/切换不再作为当前下一步。先执行 F0–F6 功能对照与运营验收，再执行 D1–D2 数据迁移演练和正式切换。详细清单见[旧 Edu 系统功能核对与修订实施方案](feature-parity-audit-and-revised-sequence.md)。

下面的 P1–P7 保留为领域建设历史编号；当前实际执行使用 F0–F6、D1、D2 编号，避免把“代码已具备”误读为“旧功能已完成替代”或“生产数据已迁移”。

| D1 数据迁移演练          | 只读画像、安全子集、全量预演、逐机构对账                          | 生成可复核迁移报告                                   | 映射、异常、重跑保护和对账通过               |
| D2 运营切换              | 停写、增量追平、验账、切换与恢复                                  | 新系统承接已批准范围，旧范围只读或明确保留           | 单一写入方、异常签字、恢复演练与运行指标通过 |

F1 → F2 → F3 → F4 → F5 → F6 是当前优先主线。数据迁移 D1/D2 不再穿插在这些功能补齐之间。P5/P6 的既有工程实现只作为基础，不代表旧功能对照已经完成。

D2 是上线工作流，不必机械等待所有明确后置功能：普通课时运营范围可先切换，前提是划定数据与用户边界。周期卡仍在使用时，必须有明确保留路径，不能让同一份权益在两边同时写入。完成全部在范围内运营迁移才可宣布整体运营替换，永远不以财务模块缺失阻塞本版验收。

### P2：机构与人员工作包

状态：2026-09-06 已完成工程实现与真实 Web 验收。生产导入仍需先运行只读计划并完成人工异常复核，详见[第二阶段迁移运行手册](phase2-organization-people.md)和[第二阶段验收报告](../acceptance/phase-two-report.md)。

1. P2.1 固化术语、机构类型、组织级学员与机构服务关系、角色及字段权限矩阵。
2. P2.2 机构 API／页面：创建、编辑、停用、查询；自营机构显式建档，不盲目回填旧空机构。
3. P2.3 学员与家长 API／页面：建档、检索、详情、绑定、解绑、绑定核实和历史。
4. P2.4 接通一期 Assignment 与真实机构／人员；查询及写操作实际使用 scope。学员跨机构服务与教师跨机构任职分别授权。
5. P2.5 在旧只读副本生成机构、人员、绑定映射及异常清单；用匿名 fixture 验证导入、重复执行、冲突拒绝。
6. P2.6 Web 验收：创建自营 A、合作 B；同一学员建立两家服务关系；家长只看自己的孩子；A 员工看不到 B 私有运营信息。

本阶段不建设课程、不发课、不接财务。迁移计划与匿名演练先行，正式导入仍遵守切换审批。

### P3：课时包、发放与账本工作包

状态：2026-09-07 已完成工程实现、隔离 PostgreSQL 迁移演练和真实 Web 验收。旧生产数据尚未导入；周期权益、过期或停用合同正余额及无法关联的赠课会被工具明确延后，详见[第三阶段迁移运行手册](phase3-lessons.md)和[第三阶段验收报告](../acceptance/phase-three-report.md)。

1. P3.1 机构课时包模板与版本，无必填金额／订单／课程。
2. P3.2 发放命令：模板发放及授权自定义发放；类型区分线下购课登记、赠送、补发、迁移期初。
3. P3.3 学员机构账户、批次、流水、只读余额查询与重算；明确唯一约束、锁顺序、时间和序号。
4. P3.4 有原因的调整、未用额度扣回、可撤销发放纠错；系统不核验资金退款。数量不足拒绝，不改历史补平。
5. P3.5 Web 账户详情、发放对话框、机构分组余额、批次来源、流水筛选和操作审计。
6. P3.6 导入适配：旧合同提取为权益批次，旧订单号仅为可追溯来源引用，不建立目标订单依赖。
7. P3.7 验收：A 发 10 再发 20 得 30，B 发 5 独立显示；重复发放不翻倍；模板修改不影响历史；扣回与消费并发安全在 P4 联合复测。

### P4：独立课次与签到消费工作包

1. P4.1 独立课次 API／页面：机构、主题、时间、状态、参与名单及预期消课数；不要求任何教学资源先存在。
2. P4.2 签到身份按课次＋学员确定，维护修订号；到场与消课结果分开，不用“学员＋日期”粗略去重。
3. P4.3 消费应用用例：从服务端解析课次机构，校验学员和权限，锁定对应账户、分摊同机构批次、原子记账。
4. P4.4 免费签到、余额不足待处理、授权补扣、撤销与改数量；同一凭证不可重复冲正。
5. P4.5 管理员／获准员工签到入口与家长查看；家长自助签到按确认的方式接入同一用例，不单独写余额。教师独立工作台在 P5，微信端在 P6。
6. P4.6 一致事务 Outbox、通知与重试；通知失败不撤销成功消课，也不重复消费。
7. P4.7 Web 验收录屏／截图和真实数据库测试：无课程建课次、签到、查流水、撤销、补扣、跨机构拒绝、并发重复请求。

应用用例顺序：校验身份与资源范围 → 校验课次和签到修订 → 决定数量 → 校验机构并锁账户 → 分摊与流水 → 签到消课结果／审计／Outbox → 提交。成功结果原子保存；业务拒绝若需保留到场事实，走独立且显式的状态处理。

### P5–P7：后续接入原则

- P5：课程和班级仅提供组织与默认值；独立课次始终可用。换老师、场地、课程不改变机构课时账户。共享教室管理时间占用，不管理租金或分账。
- P6：体验预约可以不消课；转正式只建立必要服务关系与获准发放，不能偷偷创建订单。原占位费功能排除，预约状态保留。报表只统计人数、签到、课时发放／消费、资源利用等运营指标。
- P6：家长、教师、admin-mini、微信及扫码入口按实际调用清单迁移；关联仓库或凭据缺失明确记录，不宣称已验收。
- P7：先区分限次与不限次周期权益，再确定保留、迁移或经批准转换；历史未决周期卡不能进入普通课时自动消费池。

## 6. 模块结构与统一契约

| 模块（建议名）                                | 职责                                                   | 旧来源                                                |
| --------------------------------------------- | ------------------------------------------------------ | ----------------------------------------------------- |
| organization                                  | 单组织配置、机构及类型／状态                           | organization、institutions                            |
| people                                        | 学员、家长、教师档案、家长绑定、学员机构服务关系       | people、teaching 的人员逻辑                           |
| lesson-products                               | 机构课时包模板与版本                                   | catalog/packages                                      |
| lesson-accounts                               | 发放、批次、机构账户、消费分摊、冲正、扣回、课时验账   | lesson、lesson-movements、course-contracts 的权益部分 |
| sessions / attendance                         | 独立课次、名单、签到、消课编排                         | teaching、scheduling、attendance 及各端入口           |
| teaching / facilities                         | 课程班级、报名、资源、排课增强                         | catalog、teaching、scheduling                         |
| crm / trials / learning / content / reporting | 周边运营与只读统计，按实际规模组织模块                 | 相应旧模块的非财务部分                                |
| 已有基础模块                                  | 身份、授权、审计、任务、Outbox、通知、存储、设置、品牌 | 复用 starter 与 P1                                    |

不为每个实体机械建模块。sessions 拥有课次事实，排课功能调用其公共端口，不再产生两套课次表或两个余额写入口。

API、Contract、Client 同片交付。命令区分发放、消费、冲正、扣回，不提供通用“PATCH balance”。HTTP 只做协议映射，Application 编排事务，跨模块只经 public 端口，必要时显式共享事务执行器。

用 CI 限制跨模块 Repository/schema 导入；数据库集中聚合 schema 供迁移可以保留，但不允许业务通过它任意写其他模块。内部任务与迁移导入工具也必须执行等价不变量，不能成为常规绕过入口。

## 7. 旧功能、API 与任务盘点

每个阶段建立可核对清单，而非按页面数量估算覆盖率：

- 方法＋路径、调用端、权限与字段范围、输入输出、业务规则、写表与事务、任务／外部副作用。
- 目标模块／Contract／用例、替代页面、数据映射、状态、测试证据及负责人。
- 状态限定为待迁移、已迁移、已替代、后置、范围排除；财务接口标为范围排除，不伪报已迁移。
- 覆盖后台、公开 Web、家长、教师、admin-mini、扫码、微信、定时任务、上传／文件和导出。
- 混合接口拆分：课时查询和人员数据迁移，订单／金额／支付动作移除或明确不可用；不能简单复制旧大接口。
- 新系统不代理旧财务写操作。旧支付回调、自动发课、过期任务等有可能继续影响权益，切换前必须安排关闭／保留归属，不能只删新菜单。
- starter 支付入口、API 权限、worker 任务和前端依赖进行只读盘点后定点隔离，不整库删除已有底座数据，不影响审计通知等共用能力。

本文件不是逐 API 盘点结果；未完成盘点前不提供虚构的精确总工期。先估算 P2 小工作包，后续以实际验收耗时、异常数据量和客户端范围更新排期。

## 8. 数据迁移方案

### 8.1 首要风险：机构归属

旧 schema 中 course_contracts.institution_id 可空，course_packages 通过课程／系列关联且没有直接 institution_id。因此“迁移一个机构字段”不是可靠方案。

建立归属解析报告：优先采用经核实的明确机构值，再结合历史服务关联证据生成候选。来源冲突、缺失、历史跨机构消费必须输出异常；不得根据当前老师、场地、收款方或空值直接推断成自营。

一个旧模板确实被多个机构使用时，经核对可在目标拆成多个机构模板，保留旧 ID＋目标机构的映射；每个已发放批次只能有一个确定机构。历史非法或无法解释的跨机构扣课保留原始记录并人工核定，不能伪装成新规则下合法消费。

### 8.2 导入依赖与财务解耦

1. 只读副本一致性快照、截止点、源版本、摘要与导入批次。
2. 组织／机构 → 账号及人员 → 家长绑定／员工授权／学员机构关系。
3. 机构课时模板与历史快照 → 机构账户／发放批次 → 课次及签到身份 → 历史消费凭证／分摊／流水 → 余额核对。
4. 有循环关系时先建稳定实体 ID，再补事实引用，最后完成校验；分阶段暂存数据不提前开放业务写入。
5. 课程班级、教师、场地和历史上下文按依赖补齐；来源不能重建的历史消费保存明确来源档案，不虚构课次或老师。
6. 后续导入学习内容、预约、运营记录和文件引用；周期权益独立分流。
7. 旧合同中的课时归属、数量、赠送、实际消耗保留；金额、订单、支付、退款、结算等留在受控只读归档，目标可保存旧来源标识，不建目标财务表依赖。

发生过资金退款不代表历史课时扣回可以丢掉：影响余额的权益变动仍属于迁移范围；资金事实仅归档。不能让“不做财务”变成漏导课时流水的理由。

### 8.3 历史不完整的处理

- 可验证的历史采用完整权益流水重放；不可重建时，经确认采用期初余额＋只读历史档案。
- 同一批次不能同时累计期初和期初以前的重放流水。期初前签到的纠错走专门核查用例，不对缺少分摊的历史直接自动冲正。
- 逐“学员＋机构＋批次”核对，不只看全组织课时总数。
- 检查孤儿引用、重复签到、流水不连续、余额与流水不等、负数、旧有效期、周期权益、机构不明与权限缺失。
- 纠正旧错数须有核对结论、批准人及独立调整凭证，不静默补平、修改时间、跨机构抵消或按手机号合并。
- 旧课程／班级默认课包字段只作来源，不复制为新扣课前置条件；历史实际分摊保留。
- 导入可 dry-run、可复跑、可验证，冲突停止；重放不触发通知、支付、重复发课或其他外部副作用。
- 个人资料、密码兼容和文件访问沿用 P1 安全要求，敏感信息不进入普通日志。

## 9. 切换、后置范围与恢复

建议分阶段开发验收，已批准核心范围采用受控单写切换；不实现两边同时扣同一个学员机构账户的无保障双写。

P4 后试运行优先使用匿名数据或明确无旧系统写入的新范围。若部分真实旧账户先切换，必须证明旧各端入口和任务无法再写这些账户；旧系统无法可靠隔离时，不采取部分账户生产切换。

正式窗口依次完成：备份及恢复演练 → 旧写入截止点 → 增量追平 → 逐机构课时核对 → 异常签字 → 入口切换 → 旧范围只读 → 运行巡检。

财务不迁移，但旧在线支付和自动发课链路不能成为遗漏的权益写入方。切换前核查有无在途操作；由业务方确定旧渠道收尾和线下登记流程，必要的旧回调处理保留在旧责任范围，不要求新 OMS 建支付模块。

新系统产生新发放、消课、冲正后，不能仅切回旧 URL 当作回滚。需要把新增事实可验证地补入恢复目标，或进入维护／只读并前向修复。没有增量恢复证据，不承诺无损回退。

财务归档与周期权益后置清单明确负责人员、存放位置、访问权限和使用路径；后置不等于删除。周期卡不影响无周期用户的受控上线，但影响宣称完整替代的范围。
