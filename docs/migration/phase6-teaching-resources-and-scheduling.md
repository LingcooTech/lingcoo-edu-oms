# 第六阶段：教学资源与排课字段、流程盘点

**文档状态：** 方案已实施并通过隔离数据库与真实 Web 验收；旧生产资源尚未正式导入
**核验日期：** 2026-09-08
**适用项目：** `lingcoo-edu-oms`
**旧系统：** `lingcoo-edu-system`

## 1. 本阶段结论

第六阶段不是把旧系统的 `courses`、`classes`、`class_sessions` 原样搬到 OMS，而是先把旧系统中“教学资源决定课次、课时包决定课程、班级名单决定扣课来源”的耦合拆开，再迁移仍然有运营价值的资料和历史事实。

目标模型必须明确以下边界：

1. 组织是单租户、自部署的经营主体；系统不设计多个独立组织共用一个 SaaS 数据空间。
2. 机构是教学服务和课时提供方，也是课时账户、课次和消课的服务边界。
3. 课程、校区、教室、班级、教师都只是课次的可选关联，任何一个都不是课次成立的必要条件。
4. 排课是一个“生成课次”的操作，不是一个新的课时权益系统，也不是课时包规则系统。
5. 课时包不得被课程、班级、校区、教室或教师限定。课时只按学员和机构归属，消费时明确记录消费数量和业务来源。
6. 课次是签到和消课的载体；签到事实和消课事实分离，消课仍由统一课时账本服务完成。
7. 本阶段不做小程序、不做财务、不做分成结算、不做周期卡，也不迁移旧系统的完整家长端和营销端流程。

因此，第六阶段的正确交付物应是：资源目录、课次可选关联、排课生成器和历史迁移方案。不是继续扩大旧的超级排课模块。

## 3. 旧系统实际模型与主要结构问题

### 3.1 旧系统资源关系

旧系统大致是以下结构：

```text
组织
├── 校区
│   └── 教室
├── 机构
│   └── 教师
├── 课程系列
│   └── 课程
│       ├── 默认机构
│       ├── 默认教师
│       └── 默认教室
├── 班级
│   ├── 校区（必填）
│   ├── 课程（必填）
│   ├── 主教师（必填）
│   └── 主教室（必填）
└── 课次
    ├── 班级（通常必填）
    ├── 课程（必填）
    ├── 教师（必填）
    ├── 教室（必填）
    ├── 名单
    └── 签到 + 课时包扣减
```

这个结构适合“固定课程、固定班级、固定老师、固定教室”的传统教培机构，但不适合当前的共享成长空间、合作机构入驻和资源闲置时段复用模式。

### 3.2 已确认的耦合问题

#### 课次被资源强制决定

旧 `class_sessions` 的 `course_id`、`teacher_id`、`classroom_id` 都是非空外键；后台 `POST /v1/class-sessions` 还必须先找到 `classId`。因此没有课程、教师、教室或班级时，系统无法创建一个只有“机构、时间、主题、课时数”的基础课次。

#### 班级被课时和课程决定

旧 `classes` 的课程、校区、教师、教室均为必填字段。`classEnrollments` 又要求 `billingCourseId` 和具体 `billingCourseContractId`，所以“加入班级”同时承担了分班、课程归属和扣课来源选择三个不同职责。

#### 课程目录携带了排课默认值

旧 `courses` 同时保存 `campusId`、`providerInstitutionId`、`defaultTeacherId/defaultTeacherIds`、`classroomId/classroomIds`。这些字段本来可以只是目录展示或排课建议，但旧流程将它们当成资源约束或候选过滤条件，导致课程定义反向影响课次是否能够建立。

#### 名单携带课时包选择

旧 `class_session_students`、`class_session_temporary_students` 和 `attendance_records` 都带有 `billingCourseId` 或 `billingCourseContractId`。这使得一次课次名单不只是“谁参加”，还变成了“必须从哪个课程/合同扣课”。这与通用课时的目标模型冲突。

#### 批量排课存在隐式部分成功

旧 `/v1/class-sessions/batch` 支持 `skipConflicts`，冲突课次被跳过，其余课次直接创建。若调用者没有保存返回的 `skipped` 结果，用户看到的是“排课成功”，实际却少了若干课次。排课命令还没有统一的幂等操作号和生成批次边界。

#### 历史删除风险较高

旧校区删除会级联教室和班级，班级删除会级联课次；课次删除还可能级联名单和历史事实。对于已经发生签到或消课的运营系统，这种删除路径不可接受。新系统必须采用归档和受控更正，不能通过删除资源抹掉历史。

#### 冲突逻辑与业务状态混在 Repository

旧 `findScheduleConflict` 直接读取全量非取消课次，把教师和教室冲突、课次状态、教师分配和历史数据放在同一个 Repository 中判断。新系统应将资源可用性规则放在排课领域服务，持久化只提供查询和写入端口。

## 4. 旧字段取舍

取舍含义：

- **保留**：迁移到 OMS 的正式字段或事实；
- **改名/拆分**：保留业务含义，但不能继续沿用旧的职责混合；
- **降级为可选关联**：只用于课次展示、筛选或排课建议，不影响课次成立和课时消费；
- **转快照**：历史课次保留当时名称，避免资源档案变化改写历史；
- **暂缓**：当前不迁移到第六阶段；
- **不迁移到核心**：旧字段可以留在旧系统或后续独立模块，不进入 OMS 课次核心。

| -------------------------------------------------------- | ---- | -------------------------------------------- |
| `organization.id`                                        | 保留 | OMS 单租户组织根；不引入多租户路由。         |
| `organization.name`、`brandName`                         | 保留 | 组织名称和品牌名称继续由组织设置维护。       |
| `organization.phone`、`address`、`settings`              | 保留 | 作为组织资料和运营配置，不参与课次资源约束。 |

| `startsAt`、`endsAt`                         | 保留                                        | 课次时间事实；必须满足结束晚于开始。                                                          |
| `topic`                                      | 映射为 `name`                               | 保留课次当时主题/名称；必要时另存旧字段元数据。                                               |
| `sessionType`                                | 映射为 `source`                             | `class` 通常为 `schedule`，无班级的 `ad_hoc` 为 `ad_hoc`，人工创建为 `manual`；映射需可审计。 |
| `lessonUnits`                                | 映射为 `defaultUnits` 和名单 `plannedUnits` | 只是本次服务默认消耗建议，不是课程或课时包限制。                                              |
| `status=scheduled`                           | 按迁移时点判定                              | 不能机械等同于 `open` 或 `completed`，见状态迁移规则。                                        |
| `createdByAccountId`、时间戳                 | 保留/映射                                   | 迁移为创建人、迁移来源和原始时间。                                                            |
| `class_session_students`                     | 合并为课次名单                              | 只保留学员、姓名快照、来源、计划课时和签到/消课状态。                                         |
| `class_session_temporary_students`           | 合并为名单来源                              | 记为 `session_only`，保留备注和旧 ID；不再维护两套名单。                                      |
| `billingCourseId`、`billingCourseContractId` | 从未来核心名单移除                          | 已经发生的历史消费保留旧来源引用；未发生消费的名单不因课程/合同缺失而无法保留。               |
| `attendanceRecords.status`                   | 映射为签到状态                              | 与消课状态分开迁移。                                                                          |
| `lessonDelta`                                | 不直接作为新余额操作                        | 必须与旧课时流水核对；有可靠流水才重建消费，否则进入对账队列。                                |
| `revision`、`updatedAt`                      | 保留/重新初始化                             | 新系统使用自己的乐观并发版本，历史版本作为迁移元数据保存。                                    |

## 5. 目标模型

### 5.1 最小核心模型

第六阶段完成后，最小可运行的课次模型仍然是：

```text
机构
└── 课次
    ├── 名称
    ├── 开始/结束时间
    ├── 默认消费课时数
    ├── 生命周期状态
    ├── 学员名单（可为空，后续添加）
    └── 签到与消课事实
```

课程、校区、教室、班级、教师都通过可选关联挂到课次：

```text
课次
├── 0..N 课程关联
├── 0..1 校区关联
├── 0..1 教室关联
├── 0..1 班级关联
└── 0..N 教师关联
```

第一版 UI 可以只提供每类资源最多一个主关联，但数据库和服务边界不能把它们定义成课次必填的核心外键。以后扩展多课程、协同教室或资源组合时，不需要重写课时账本。

### 5.2 课次与机构

`teaching_sessions.institution_id` 是课次唯一必要的业务边界字段。它回答的是“这次服务由哪家机构提供”，而不是“这次课使用了哪门课程”。

每个关联对象如果存在机构归属，必须满足：

```text
关联资源没有机构范围       -> 可以关联，但按组织级资源处理
关联资源有机构范围且相同   -> 可以关联
关联资源有机构范围且不同   -> 拒绝关联，并返回明确冲突
```

这只是防止机构越界，不是把资源关系变成课次创建前置条件。没有课程、校区、教室、班级或教师时，课次仍然可以创建和进入点名流程。

### 5.3 建议的关联事实

需要在后续实现阶段增加的关联事实应使用模块自己的表或受控端口，而不是让 Route 直接访问别的模块 Repository：

- `teaching_session_courses`
  - `session_id`、`institution_id`、`course_id`；
  - `course_name_snapshot`；
  - 可选 `is_primary`；
  - 创建人、创建时间和审计信息。
- `teaching_session_campuses`
  - 第一版可以实现为课次上的可空关联；
  - 保存 `campus_name_snapshot`；
  - 同一课次最多一个实际场地校区。
- `teaching_session_classrooms`
  - 第一版可以实现为课次上的可空关联；
  - 保存 `classroom_name_snapshot`、校区快照；
  - 仅在有关联时参与教室冲突检查。
- `teaching_session_classes`
  - 第一版可实现为课次上的可空关联；
  - 保存 `class_name_snapshot`；
  - 不自动复制或要求班级扣课账户。
- `teaching_session_teachers`
  - 已在第五阶段建立；
  - 支持 `instructor` 和 `assistant`；
  - 保存教师姓名快照和分配人。

关联表的共同约束：同一关联不能重复；历史课次保存名称快照；删除资源不会删除课次事实；归档资源不能被新排课使用，但历史关联可继续展示。

### 5.4 课时包与资源完全解耦

课时包和课时账户继续遵守第四阶段规则：

```text
学员 + 机构 = 机构课时账户
```

课程、校区、教室、班级、教师关系只影响教学运营信息，不加入课时包的可用条件。消课请求至少包含：

- 机构；
- 学员；
- 课次/签到记录或其他明确业务来源；
- 正整数消费数量；
- 操作人；
- 幂等操作号和原因。

如果未来不同服务事件需要消耗不同数量的通用课时，数量应由课次、规则配置或人工确认明确给出，并写入消课流水；不能通过课程绑定或修改课时包范围来隐式实现。

## 6. 不变量

以下不变量在 Contract、应用服务、数据库约束和集成测试中都必须得到保护：

### 6.1 组织和机构

1. 一次部署只对应一个组织运营空间。
2. 机构是课时服务边界，不是独立租户。
3. 课次必须属于一个有效机构；课程等资源可以为空。
4. 机构 A 的课时账户、批次、流水不能被机构 B 的课次消费。
5. 机构停用不删除历史账户、课次、签到和流水。

### 6.2 资源关联

1. 课程、校区、教室、班级、教师均可不关联。
2. 任何资源关联都不能改变课时账户所有权或消费范围。
3. 资源有关联机构时，必须与课次机构一致；无机构范围的资源按组织级资源处理。
4. 教师必须通过教师-机构关系和课次分配获得教师工作域，不能仅凭教师档案 ID 访问课次。
5. 资源档案名称变化不能改写已发生课次的名称快照。
6. 归档资源不能用于新的课次关联，但不能删除已有历史关联。

### 6.3 课次和名单

1. `endsAt > startsAt`。
2. 课次状态只能按允许的状态机迁移，不能从 `completed/cancelled` 重新打开。
3. 同一课次同一学员只能有一条有效名单记录。
4. 名单可以没有课程、教师、校区、教室或班级上下文。
5. 名单的 `plannedUnits` 是本次事件计划消耗值，不是课时包余额，也不自动产生扣课。
6. 签到与消课状态分离；点名成功不等于消课成功。
7. 已发生有效消课的课次不能直接取消，必须先按流水冲正。
8. 已经产生签到或消课的课次，不允许无审计地修改影响历史语义的字段。

### 6.4 排课

1. 排课只负责生成课次；不创建、修改或限定课时包。
2. 单次排课命令的每个发生日期最终对应一个独立课次。
3. 重试同一排课命令不能生成重复课次。
4. 批量排课必须有预览/校验结果和明确的提交边界。
5. 教师或教室为空时，不产生对应类型的资源冲突；时间和机构仍必须有效。
6. 资源冲突不能通过自动改写教师、教室或课时数量来“解决”。
7. 已取消课次不参与未来资源冲突；已完成历史课次不阻止新的未来排课。

## 7. 状态规则

### 7.1 课次生命周期

目标沿用 OMS 当前的四态模型：

```text
draft ──open──> completed
  │              ▲
  └──cancel──────┘
open ──cancel──> cancelled
```

具体规则：

- `draft`：可以调整名称、时间、默认课时和可选资源关联；可以没有任何资源关联和名单。
- `open`：进入实际服务和点名状态；可补充合法名单、教师和场地关联，但涉及已发生事实的改动必须受控并审计。
- `completed`：课次结束，名单和历史资源语义只读；如需纠错，走更正/冲正流程。
- `cancelled`：保留取消原因和时间；不再接受签到和消费；已有消费必须先冲正。

完成课次前，所有名单必须不再是 `pending`；“请假/缺勤”不代表已消课。完成课次不会自动为所有到课学员扣课，消课仍是独立、幂等、可追溯操作。

### 7.2 资源状态

校区、教室、教师、课程和班级统一采用至少 `active/archived` 两类运营状态：

- `active`：可以被新的资源关联或排课选择；
- `archived`：不能用于新的排课，但历史课次和快照仍可读取。

旧系统 `classes` 的 `recruiting/active/completed/paused/archived` 可以保留为班级域自身状态，但不能映射为课次生命周期。旧 `scheduled` 只表示旧系统的排课状态，必须结合实际时间、签到和消课数据迁移。

## 8. 冲突规则

### 8.1 时间合法性

所有手工和批量排课都必须满足：

```text
开始时间 < 结束时间
```

批量排课必须以明确时区解析日期和时间。不能依赖浏览器本地时区或服务器默认时区，否则同一批课次在不同环境会发生日期漂移。

### 8.2 教师冲突

如果新课次关联了教师，则与该教师已有的有效计划发生重叠时产生冲突；多教师课次只要任一教师重叠，就视为教师冲突。

第一版默认规则：

- `draft`、`open` 的课次参与计划冲突检查；
- `completed`、`cancelled` 不参与未来排课冲突；
- 新课次无教师时不做教师冲突检查；
- 教师分配调整同样必须重新检查冲突。

若以后确实需要临时重叠，必须使用显式 `allowConflict` 或管理员覆盖命令，并且要求填写原因、记录审计，不得通过普通保存接口静默绕过。

### 8.3 教室冲突

如果新课次关联了教室，则同一教室时间重叠产生冲突。没有教室的课次可以先保存，后续关联教室时再检查。教室容量只作为名单容量提示，不能把“容量不足”误判为课时不足，也不能阻止没有固定班级的临时课次。

### 8.4 校区和教室一致性

如果课次同时关联校区和教室，教室必须属于该校区。若只关联教室，可以从教室档案展示其所属校区，但不能把校区字段强行写回课次作为必填值。

### 8.5 机构一致性

课次机构是唯一权威边界。课程提供机构、教师任职机构、班级机构或教室可用机构存在时，必须与课次机构一致；没有配置机构范围的组织级资源可以被多个机构的课次引用，但其引用关系仍然分别审计。

## 9. 排课流程目标

### 9.1 手工创建课次

```text
选择机构
  -> 填写名称和时间
  -> 可选关联课程/校区/教室/班级/教师
  -> 校验资源状态、机构一致性、时间冲突
  -> 创建 draft 课次
  -> 管理员打开课次
  -> 添加名单
  -> 签到
  -> 按业务需要独立消课
  -> 完成或取消
```

任意一步都不能要求用户先创建课程、班级或课时包。若运营人员只想记录一场没有课程名称的服务事件，也可以直接建立课次并完成签到消课。

### 9.2 批量排课

排课计划可以作为可复用模板持久化，但它只保存未来生成课次所需的默认值，不能成为长期控制历史课次的“父记录”。计划编辑只影响之后的生成命令，已经生成的课次保持独立：

1. 输入机构、日期范围、时区、每日/每周规则、时间、名称、默认课时数和可选资源；
2. 生成每个发生日期的候选课次；
3. 对每个候选课次执行时间、机构、资源状态和教师/教室冲突检查；
4. 返回预览结果：将创建的日期、冲突日期和冲突原因；
5. 用户确认后，以幂等 `operationId` 提交；
6. 每个发生日期写入一条独立 `teaching_session`，来源为 `schedule`；
7. 默认不复制班级成员；只有操作人明确选择时，才把生成当时的班级有效成员复制成独立课次名单；
8. 返回创建结果和明确的批次统计。

默认提交策略应为“有冲突则整批不提交”，避免旧系统 `skipConflicts=true` 造成用户不知情的部分成功。以后如果要支持“跳过冲突继续创建”，必须成为明确的用户选项，返回完整 skipped 列表，并以相同幂等号保证重试稳定。

批量排课默认只生成课次，不自动创建名单、不自动签到、不自动消课、不创建课时包，也不为课程、班级或教师生成隐式绑定。显式复制班级成员只是一项便捷操作；复制完成后，课次名单与班级成员分别演进，后续班级增减成员不得静默改写既有课次名单。

## 10. 历史数据迁移策略

### 10.1 先做数据画像，再做写入

实施前必须从旧数据库导出只读画像，至少统计：

- 组织和机构数量；
- 课程、课程系列、校区、教室、教师、班级数量及归档比例；
- 课次中课程/教师/教室/班级为空或引用失效的数量；
- 教师单机构字段与实际合作关系的冲突；
- 课次教师/教室时间重叠数量；
- 班级容量超限数量；
- 名单重复、临时学员与正式学员重复数量；
- `attendanceRecords.lessonDelta` 与旧课时流水、合同余额的差异；
- 已删除或无法解析的课程、教师、教室、机构引用；
- 旧课次状态与实际时间、签到、消课事实不一致的数量。

画像结果必须形成迁移报告和异常清单，不能在导入脚本中静默猜测。

### 10.2 推荐迁移顺序

1. **建立 ID 映射和原始来源表**：保存旧表名、旧 ID、目标 ID、迁移批次、原始载荷哈希和异常状态。
2. **迁移组织和机构**：先建立单租户组织及全部机构，确认自营机构和合作机构边界。
3. **迁移教师档案及教师-机构关系**：单值 `institutionId` 先导入主关系，额外合作关系通过画像或人工补录；不影响课次导入。
4. **迁移校区和教室**：保留地址、地理坐标、图片、容量和状态；历史引用资源不得物理删除。
5. **迁移课程系列和课程目录**：保留展示字段；将课程上的默认校区、教师、教室降级为偏好，不生成课时包限制。
6. **迁移班级档案**：只迁移班级身份、名称、容量、状态和可选课程关系；入班计费来源暂不驱动 OMS 名单。
7. **迁移课次核心**：为每条旧课次建立 OMS 课次，明确推导机构；无法确定机构的进入人工异常队列，不能默认写入某个机构。
8. **迁移课次可选关联**：课程、校区、教室、班级、教师分别写入可选关联和名称快照；缺失或失效关联不阻断课次核心迁移。
9. **迁移名单和签到**：正式、临时名单合并，保留来源和旧 ID；学员姓名写入快照。
10. **迁移历史消课**：仅在旧课时流水、余额、合同和签到可以相互证明时重建 OMS 消费流水；否则只迁移签到事实和旧来源元数据，列入对账队列。
11. **验证守恒和可追溯性**：逐机构、逐学员、逐课次核对余额、流水、签到和名单数量。
12. **双读/灰度观察**：先让 OMS 管理端读取迁移结果，旧系统继续运行；通过验收后才考虑停止旧排课写入。

### 10.3 `scheduled` 状态迁移不能机械映射

旧系统只有 `scheduled/completed/cancelled`，OMS 使用 `draft/open/completed/cancelled`。建议采用以下迁移决策：

| 旧状态      | 条件                       | 目标状态               | 说明                         |
| ----------- | -------------------------- | ---------------------- | ---------------------------- |
| `completed` | 有可靠结束事实             | `completed`            | 只读历史。                   |
| `cancelled` | 有取消事实                 | `cancelled`            | 保留取消原因/原始状态。      |
| `scheduled` | 未来且尚未进入运营         | `draft`                | 迁移后由运营人员确认并打开。 |
| `scheduled` | 当前正在发生或需要立即点名 | `open`                 | 必须记录迁移决策人。         |
| `scheduled` | 已经有签到或有效消课       | `completed` 或人工异常 | 不能只看旧状态，按事实修复。 |

不得因为“旧状态是 scheduled”就自动将所有课次打开或完成。

### 10.4 历史扣课的处理原则

旧签到中的 `lessonDelta < 0` 不能直接转换成新的 `consume` 流水，因为它可能只是旧系统的余额修正、重复扣课或与合同余额不一致。

每条历史扣课必须检查：

1. 是否能找到对应学员和机构；
2. 是否能找到原课次和名单；
3. 是否存在对应旧课时合同/账户；
4. 旧课时流水是否包含相同操作来源；
5. 旧余额与流水是否守恒；
6. 是否已经发生冲正或重复扣减。

通过全部检查才可以用迁移专用幂等号创建历史消费流水；否则迁移签到事实，但将消费状态标记为待对账，不为了让余额“看起来正确”而猜测或自动扣课。

## 11. 实施顺序

第六阶段实际实施建议拆成以下小步骤，每一步都可单独验收：

### 6A：资源与历史数据画像

- 建立旧字段清单、来源映射和异常报告；
- 对旧数据库做只读统计；
- 确认自营机构、合作机构、教师合作关系和资源归属；
- 不改现有 OMS 生产表。

### 6B：资源目录模块

- 增加课程系列、课程、校区、教室和班级的独立模块；
- 每个模块拥有自己的 Contract、领域服务、Repository 和审计；
- 资源归档替代物理删除；
- 资源之间的默认关系只作为偏好或目录关系，不直接写入课时账本；
- 教师档案沿用 P2，补齐教师-机构多关系端口。

### 6C：课次可选关联

- 在不破坏当前课次、签到和消课的前提下增加可选资源关联；
- 首先实现教师关联已有能力的统一化；
- 再加入课程、校区、教室、班级关联；
- 所有关联保存快照和审计；
- 关联机构不一致时拒绝，关联缺失时允许课次继续运行。

### 6D：单次手工排课

- 新增一个排课应用服务，只接收机构、时间、名称、默认课时和可选资源；
- 资源冲突检查由该服务完成；
- 生成 `source=schedule` 的课次；
- 不生成课时包、不改变课时余额、不自动选择扣课来源；
- 增加机构隔离、资源归档、冲突和并发测试。

### 6E：批量排课

- 实现日期展开、时区、预览、提交和幂等；
- 默认整批原子提交；
- 如支持跳过冲突，必须显式选择并返回完整结果；
- 每个发生日期生成独立课次，未来可以单独调整或取消；
- 不把重复规则强行作为课次父对象。

### 6F：班级和名单独立迁移

- 迁移班级档案和可选课程关系；
- 课次可以引用班级，但名单不再强制来自班级；
- 班级入班和课次名单分别维护；
- 不复制旧 `billingCourseId/billingCourseContractId` 为新课次的必需字段；
- 学员加入名单只验证学员-机构关系和课次状态。

### 6G：历史课次和签到迁移

- 先迁移核心课次，再迁移可选关联和快照；
- 合并正式/临时名单；
- 分离签到事实与历史扣课；
- 对无法核验的历史扣课进入对账队列；
- 形成逐机构、逐学员、逐课次的迁移验收报告。

### 6H：后台运营界面

- 资源目录使用统一 Modal 表单；
- 课次创建页先展示机构、名称、时间和默认课时，再提供可选资源；
- 排课页支持单次、批量、预览、冲突解释和操作记录；
- 课时余额和消费入口不放进课程、班级、教室或教师编辑表单；
- 本阶段不改小程序。

### 6I：旧系统切换

- 旧系统继续作为现网系统运行，先完成只读迁移和双读核对；
- 禁止两个系统同时无协调地写同一批未来课次；
- 先切换资源和排课写入，再切换签到，最后切换消课；
- 每一步保留回滚窗口和旧 ID 映射；
- 迁移未验收前，不删除旧数据，不执行破坏性清理。

## 12. API 和模块边界要求

第六阶段必须避免旧系统的直接 Repository 共享。建议的模块边界如下：

```text
organization
  -> 提供单租户组织与机构目录
people
  -> 提供学员、教师档案及机构关系快照
teaching-resources
  -> 提供课程、校区、教室、班级目录
lesson-sessions
  -> 提供课次、名单、签到、消课关联
scheduling
  -> 只负责编排资源、检查冲突、生成课次
lesson-accounts
  -> 唯一负责课时账户、批次、流水和冲正
audit/idempotency/outbox
  -> 提供统一横切能力
```

约束：

- Route 只做解析、授权和调用应用服务；
- 排课模块不能直接写课时账户或课时流水；
- 资源模块不能直接修改课次名单和消费状态；
- 课次模块不能直接更新课时余额；
- 机构和人员模块只通过公开端口提供有效关系和快照；
- Contract 统一定义资源关联、排课预览、排课提交和冲突错误码；
- 所有写操作都要有审计、幂等和乐观并发边界。

建议的接口族：

- `GET/POST/PATCH /api/resources/courses`；
- `GET/POST/PATCH /api/resources/campuses`；
- `GET/POST/PATCH /api/resources/classrooms`；
- `GET/POST/PATCH /api/resources/classes`；
- `GET/POST/PATCH /api/institutions/:institutionId/lesson-sessions`；
- `POST /api/institutions/:institutionId/schedules/preview`；
- `POST /api/institutions/:institutionId/schedules/commit`；
- `PUT /api/institutions/:institutionId/lesson-sessions/:sessionId/associations`。

具体 URL 仍以实现阶段 Contract 评审为准，本文件不授权提前修改 API。

## 13. 明确不做

第六阶段不包括：

- 微信小程序教师工作台、家长端或任何小程序改造；
- 财务模块、支付、代收、合作机构分成、结算批次；
- 周期卡和按时间有效的复杂权益；
- 课程绑定课时包或按课程限制通用课时；
- 多租户 SaaS、多个组织共用数据库；
- 把班级变成课次父实体或把入班变成扣课前置条件；
- 试听预约、营销二维码、线索转化和公开课程销售流程；
- 作业、评价、互动、通知等围绕旧 `class_sessions` 的外围功能；
- 旧系统所有历史脏数据的自动猜测式修复；
- 为了迁移方便而直接删除旧表或覆盖旧系统生产数据。

## 14. 本阶段验收标准

在进入编码前，必须由产品和技术共同确认：

1. 可以只提供机构、课次名称、时间和默认消费课时，成功创建课次；
2. 不提供课程、校区、教室、班级和教师，课次仍可打开、加学员、签到和按明确数量消课；
3. 任意资源关联都不会改变课时包的机构边界和可消费范围；
4. 课程、校区、教室、班级和教师都可以被归档，历史课次仍可追溯；
5. 教师和教室时间冲突能被明确识别，冲突结果不会静默部分成功；
6. 批量排课可预览、可幂等、可解释，生成的是独立课次；
7. 跨机构资源和课时操作被数据库或服务端阻断；
8. 旧课次、名单、签到和历史消费可以通过来源映射追溯；
9. 历史扣课无法核验时不会伪造新的消费流水；
10. 小程序和财务范围没有被第六阶段实现偷偷带入。

## 15. 结论与下一步

旧系统的课程、校区、教室、班级和教师字段本身大多有运营价值，不能简单删除；真正需要重构的是它们在课次上的职责：从“必填、决定课次和扣课”改为“可选、提供上下文和排课建议”。

当前 OMS 的课时账本和课次核心已经具备正确的底层方向；第六阶段已按 `6A -> 6B -> 6C -> 6D` 完成资源模块、可选关联、排课生成和 Web 验收。批量排课的工程能力已验证，但旧生产资源、班级和历史课次仍需按只读画像、异常核对和正式迁移窗口处理。

本文件既是第六阶段的规则与迁移细则，也明确：工程验收完成不等于旧生产资源已经导入。
