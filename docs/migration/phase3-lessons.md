# 第三阶段迁移运行手册：机构通用课时与账本

更新日期：2026-09-07。

## 结论与适用范围

P3 工具把旧系统中可核验的普通课时余额迁为“学员＋机构”账户的一笔或多笔期初发放。工具不迁移金额、订单、支付或分账，也不会把课程、班级、教师、校区或教室变成课时使用条件。旧订单、合同、课程和班级标识只保存在批次的来源证据中。

当前只完成工具和隔离数据库演练，尚未对旧生产库执行。P1 身份与 P2 机构／人员必须先完成，目标机构和学员 ID 必须已存在。

## 目标模型

- `lesson_package_templates`：机构课时包当前版本；修改采用乐观修订。
- `lesson_package_versions`：不可变模板版本，已发放批次引用版本快照。
- `lesson_accounts`：一个学员在一个机构的余额投影。
- `lesson_batches`：每次发放形成独立批次，保存剩余量和旧来源证据。
- `lesson_movements`：不可更新、不可删除的增减流水。
- `lesson_movement_allocations`：扣减或未来消费对批次的明确分摊。

数据库在事务提交时核对：账户余额等于流水增加减扣减，也等于批次剩余总和；账户累计值和最后序号必须与流水一致；扣减分摊必须等于扣减流水数量且不得跨账户。

## 映射规则

1. 合同明确的 `institution_id` 优先；为空时才采用课程的服务机构证据。两者都缺失时不猜测，标记 `LESSON_INSTITUTION_UNRESOLVED`。
2. 普通课时包按“旧课时包＋目标机构”生成机构模板和不可变 V1；一个旧模板跨机构使用时会拆成多个目标模板。
3. 有正余额且仍有效的普通课时合同形成期初 `grant` 流水和 `migration_opening` 批次。期初数量只取当前剩余课时，不重放期初之前的历史消费，避免重复计算。
4. 旧合同号、订单、课程、班级、课包、原始课时、起止时间写入 `source_metadata` 作为证据，不建立目标财务或教学外键。
5. 同一学员同一机构的多份合同合并到账户，但各自保留批次和来源编号。
6. 零余额合同不创建账户批次；工具在例外统计中记录。周期权益不折算为普通课时。

## 预检与停止条件

以下合同级问题会把对应合同或记录放入延后清单，不写入目标；只要没有其他全局硬阻断，其他合同仍可安全迁移：

- 旧流水链断裂、前后余额不连续或最终余额与合同余额不一致；
- 缺少旧流水证据；
- 已停用／已取消／已过期合同仍有正余额；
- 周期卡或周期权益；
- 机构归属无法确定；
- 没有生成目标合同关系的赠课记录。

以下仍是全局硬阻断，计划不会执行任何目标写入：

- 数量非整数、为负数或剩余大于原始数量；
- 旧操作编号重复；
- P2 目标机构或学员缺失；
- 目标 P3 表结构不完整或任一目标课时表已经有数据。

应用安全子集时，对合同级延后项必须人工确认并使用 `--allow-incomplete`。

缺少旧流水证据会进入例外统计，不会被静默忽略。正式导入前应按合同逐项核验；若无法重建完整历史，可在批准后采用期初余额，但不能同时重放同一余额形成之前的历史流水。

## 执行步骤

先连接旧库的只读一致性副本和已完成 P2 的空 P3 目标库：

```bash
export MIGRATION_SOURCE_DATABASE_URL='postgresql://readonly:***@source/legacy_edu'
export MIGRATION_TARGET_DATABASE_URL='postgresql://migration:***@target/lingcoo_edu_oms'
```

只读计划不会修改目标库，输出只包含摘要与分类计数，不包含姓名、合同号或 UUID：

```bash
corepack pnpm migration:lessons:plan
```

保存完整命令输出和目标指纹，人工处理 blocker、incomplete 与 exception。确认目标、备份和停写窗口后应用：

```bash
node scripts/migration/lesson-phase3.mjs apply \
  --apply \
  --confirm-target '<plan 输出的 targetFingerprint>'
```

若业务负责人已经签字接受延后项，再显式增加：

```bash
node scripts/migration/lesson-phase3.mjs apply \
  --apply \
  --allow-incomplete \
  --confirm-target '<plan 输出的 targetFingerprint>'
```

保护措施包括：源目标同库拒绝、源库只读快照、目标指纹确认、目标非空拒绝、单事务写入和提交时数据库对账。应用失败会回滚全部 P3 写入。

## 演练与应用后核验

本地隔离 PostgreSQL 演练：

```bash
MIGRATION_INTEGRATION_ADMIN_URL='postgresql://admin:***@127.0.0.1/postgres' \
  corepack pnpm test:migration:db
```

应用后至少核验：

- 逐“学员＋机构”比对目标余额与已批准源余额；
- 账户余额、累计增减、流水、批次剩余量全部守恒；
- 每个期初批次有唯一 `course_contract:<旧合同 ID>` 来源；
- A／B 机构余额严格隔离；
- 模板版本和流水不能更新或删除；
- 重跑计划必须因目标非空而停止；
- 导入过程没有触发通知、支付或重复发课副作用。

## 切换与恢复

在 P4 签到消课上线前，旧系统仍可能是课时写入方。正式切换必须先关闭旧发课、扣课、退款扣回和定时任务写入口，再做增量追平和逐机构签字。目标一旦产生新发放或扣减，不能仅切回旧 URL；应进入维护／只读并前向修复，或把新增不可变事实完整补入恢复目标。

周期权益和其他延后记录必须有负责人、处理状态和可访问的旧系统路径，不能因普通课时迁移而消失。
