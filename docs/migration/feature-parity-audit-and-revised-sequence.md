# 旧 Edu 系统功能核对与“先补功能、后迁数据”实施方案

更新日期：2026-09-09
适用项目：`lingcoo-edu-oms`
对照项目：`/Users/admin/Projects/Industry-solutions/Edu-system-solution/lingcoo-edu-system`

## 1. 当前决策

本项目从现在开始调整为：

> **先做旧系统逐模块功能核对，补齐目标范围内的功能和运营闭环；暂不执行正式数据迁移；待功能验收和实际运营演练通过后，再统一做数据迁移、对账、切换。**

因此，以下动作暂时冻结：

- 不向 OMS 正式导入旧生产数据；
- 不进行旧系统停写、增量追平或生产切换；
- 不因为已有隔离库迁移演练而认为对应功能已经完成迁移；
- 不把旧系统所有页面机械复制到新系统；
- 不把订单、支付、退款金额、分成结算和周期卡作为当前核心闭环的前置条件。

已有的隔离数据库和 fixture 演练仍然保留，作用改为验证数据结构和迁移工具，不作为正式运营数据。既有阶段验收报告不改写，本文件记录新的执行顺序。

## 2. 为什么必须先做功能核对

旧系统的后台页面和后端模块存在历史演进关系，并非当前目标菜单的一一映射。例如：

- 旧 `teaching/index.ts` 约 4,487 行，同时承载教师、机构、学员关联、教学档案和部分课次相关能力；
- 旧系统包含 `content`、`crm`、`course-contracts`、`finance`、`payment`、`refund`、`report`、`trial`、`admin-mini` 等当前 OMS 尚未全部接入的模块；
- 旧后台同时存在课程、系列课程、课程资源、课程合同、订单、试听、营销、内容、报表等页面；
- OMS 已经完成的是新的领域底座和核心运营闭环，不等于旧系统每一个用户可见功能都已经有替代路径。

如果此时直接迁移数据，容易出现“数据已经进来了，但操作入口、权限、业务规则或客户端还没有对应能力”的半迁移状态。此状态比暂不迁移更难核对，也会掩盖实际运营问题。

## 4. 旧模块逐项核对结论

状态含义：

- **已迁移（E）**：目标能力已有新模块、API、页面和相应验收；仍需后续统一数据迁移。
- **部分迁移（P）**：底层或部分页面已经存在，但还不能覆盖旧系统的完整运营路径。
- **待补齐（M）**：属于已确认范围，必须在数据迁移前完成。
- **后置（D）**：功能有业务价值，但不阻塞当前“机构—学员—课时—课次—签到消课”核心运营。
- **排除（X）**：经当前经营决策明确不建设或不接入，不作为迁移缺口。

## 5. 当前真正的功能缺口

当前不应继续泛化为“先迁 P8 数据”。在数据迁移之前，至少需要完成以下闭环：

### M1：人员与权限可运营

- 组织、机构、学员、家长、教师的旧字段核对；
- 新建学员自动创建课时账户，并在同一引导流程中明确发课入口；
- 家长绑定、解绑、核实和可见范围；
- 教师账号与教师档案、机构任职、课次分配的真实关联；
- 管理员、机构人员、教师、家长的列表、详情、写入和敏感字段权限。

### M2：课时账本可运营

- 机构通用课时包，不绑定课程、班级、教师、校区或教室；
- 学员＋机构唯一课时账户；
- 发放、补发、扣回、调整、消费、冲正均有不可变流水；
- 账户、批次、流水、审计在实际操作后能对账；
- 重复请求、并发扣课、余额不足、失败重试不会重复记账。

### M3：课次与签到消课可运营

- 没有课程、班级等资源时也能创建独立课次；
- 课次可以关联课程、班级、教师、校区、教室，但这些关联不改变课时归属；
- 单个点名和批量点名；
- 到场事实和消课事实分离；
- 不消课签到、余额不足待处理、授权补扣、撤销/冲正等路径有明确状态；
- 每次消费能追溯到课次、学员、机构、批次、数量、操作人和时间。

### M4：教学组织不再依赖超级文件

- 教学资源、排课、课次、签到各自有独立用例和 Contract；
- API Route 不直接编排跨模块 Repository；
- 课程、班级、资源关联只作为上下文，不成为课时系统隐式规则；
- 后续教师工作台可以调用与后台相同的签到/消课用例。

## 6. 调整后的实施顺序

### F0：功能清单基线与冻结迁移（当前阶段）

产出：本文件、旧模块/页面/API 清单、目标状态字段、迁移/替代/后置/排除决策。

出口条件：每个旧模块都有明确处理结论；未决项有负责人和验收标准；确认没有正式数据迁移任务在后台运行。

### F1：核心人员和机构功能补齐

范围：组织设置、机构、学员、家长绑定、教师档案、账号授权、旧字段补齐。

方式：以旧系统现有字段和实际操作路径为对照，后端保持独立用例，后台提供连续引导流程。完成后用全新测试数据进行真实操作，不导入旧生产数据。

出口：可以从零开始建立组织、机构、学员、家长、教师，并让不同角色只能看到允许的数据。

### F2：课时账本完整运营闭环

范围：课时商品/课时包、课时账户、发课、扣回、调整、流水、审计、余额核对。

出口：可以用测试数据完成多机构、多批次、重复提交、并发和纠错场景；任何余额变化都有来源和操作记录。

### F3：课次、排课和签到消课完整运营闭环

范围：独立课次、课程/班级/教师/校区/教室可选关联、排课计划、名单、单个/批量签到、消课、撤销、补扣、余额不足处理。

出口：业务人员可以连续演练“建学员 → 发课 → 安排教学 → 建课次 → 点名 → 消课 → 查流水 → 纠错”。

### F4：教师工作域和新客户端接入

范围：教师真实身份、机构授权、课次分配、教师点名工作台和批量点名；旧小程序保持不动，新客户端另行副本开发和验收。

出口：教师用真实测试账号完成点名，结果与管理端、课时流水一致；异常网络和重复提交可安全重试。

### F5：非核心旧功能逐项决策

按招生转化、内容、试听、报表、通知、系统集成等模块逐项决定：迁移、重构替代、延后、只读保留或排除。不得因为旧页面存在就自动列为当前上线前置。

出口：所有仍需保留的旧功能有目标入口、API Contract、权限、数据来源和验收场景。

### F6：新系统完整功能验收与运营演练

使用全新测试数据和业务人员，至少演练：新建学员、家长绑定、发课、换机构服务、排课、调课、单个点名、批量点名、余额不足、撤销、流水核对、权限越权、重复点击和失败重试。

出口：连续运营一段时间后没有阻塞性业务问题；遗留问题分为必须修复、可接受、后置三类并签字确认。

### D1：统一数据迁移演练

只有 F0–F6 通过后，才重新启动数据迁移：先只读画像，再安全子集，再全量预演，再按机构对账。迁移脚本必须支持重复执行保护、异常隔离和结果报告。

### D2：正式迁移、停写和切换

完成旧系统停写窗口、增量追平、机构/学员/账户/流水/课次对账、异常签字、恢复演练和单一写入方切换后，才进入正式运营。

## 7. 数据迁移暂缓期间的原则

- 测试数据可以创建、修改和清理，但必须使用明确的测试组织/机构标识；
- 旧系统只读检查可以继续，不能把检查脚本升级成导入脚本；
- 隔离库迁移演练可以保留，用于验证 Schema、映射和报告，不代表生产数据已迁移；
- 发现旧系统异常时只形成问题清单和来源证据，不在本阶段直接篡改旧记录；
- 新功能不得为了兼容旧脏数据而破坏新的课时核心规则；
- 任何后置功能如果会影响核心课时事实，必须先单独建模并通过规则评审。

## 8. 下一项具体工作

下一项不做数据导入，按 F1 开始：

1. 建立旧字段、API、页面操作路径与 OMS Contract 的对照清单；
2. 先补齐机构、学员、家长、教师的旧字段和真实授权边界；
3. 用全新测试数据验证“新建学员自动创建账户 → 发放机构课时”的连续流程；
4. 通过后再进入课时账本的多机构、多批次和纠错测试。
