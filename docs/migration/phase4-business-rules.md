# P4 课时、课次、签到与消课业务规则

**文档状态：** 当前实现基线与后续扩展约束
**适用系统：** Lingcoo Edu OMS 运营管理系统
**适用阶段：** P1 身份与权限、P2 组织与人员、P3 机构课时、P4 课次与签到消课
**核验日期：** 2026-09-08

## 1. 文档目的

本文档是 P4 领域的正式业务规则基线，用来说明当前代码已经实现的规则、数据库必须守住的事实约束、当前尚未开放的访问边界，以及后续教师工作域等功能应遵循的扩展方向。

本文档不是产品宣传说明，也不是旧系统字段清单。凡是涉及余额、机构归属、签到、消课、撤销和权限的规则，均应以本文档和对应的领域服务、数据库约束、接口 Contract 共同作为验收依据。

当前最小可运行经营闭环是：

```text
组织建立运营空间
  -> 机构作为教学服务方
  -> 学员与机构建立服务关系
  -> 为学员发放该机构课时
  -> 创建该机构课次
  -> 将学员加入课次名单
  -> 签到
  -> 按明确课时数消课
  -> 查询流水、必要时冲正并重新处理
```

上述闭环不要求课程、班级、教师、校区、教室、订单、支付或财务分账存在。它们可以在后续作为课次的来源或可选关联加入，但不得成为普通课时稳定性和消课正确性的隐含前提。

## 2. 经营模型与术语

### 2.1 组织

组织是一次自部署实例对应的经营主体，也可以理解为技术上的单租户边界。当前系统一个部署服务一个组织，不提供多个相互独立的组织共用同一 SaaS 运行空间的运营能力。

组织配置包括名称、品牌名称、Logo、联系方式、地址和运营模式。运营模式可以表达“纯自营”或“自营＋合作机构”，但它不改变课时账本的机构隔离规则。

当组织为纯自营时，业务界面可以不要求用户区分“自营”和“合作机构”；但技术上仍使用机构模型承载教学服务边界。自营教学服务应有明确的自营机构记录，而不是使用空机构、特殊机构 ID 或绕过机构校验来表示自营。

### 2.2 机构

机构是教学服务和课时提供方，是课时权益的业务边界。机构可以是：

- 组织自身经营的自营教学主体；
- 入驻组织经营空间的合作教学机构；
- 在组织管理范围内提供课程服务和课时服务的其他教学方。

机构不是技术租户，不是独立部署，也不是收款账户。当前机构模型包含名称、类型、状态、联系人、联系方式、地址、Logo、介绍、资质与成果展示、排序和备注等档案字段。

机构停用不得删除其历史学员关系、课时账户、课时批次、课时流水、课次、签到或消课记录。停用后的新增业务策略可以限制后续操作，但历史事实仍须可追溯。

### 2.3 学员

学员是组织级人员档案，是课时的所有者。学员档案可以包含姓名、称呼、年级、学校、性别、出生日期、备注和状态等字段。

学员与机构之间另有服务关系。该关系表达“此学员可以在此机构接受服务并拥有此机构课时账户”，不复制学员档案，也不把学员变成机构的独立所有者。

学员可以同时与多个机构建立有效服务关系，因此同一个学员可以同时存在多个机构课时账户，但每个账户必须分开查询、分开扣减、分开追溯。

### 2.4 家长

家长是独立的监护人档案，与学员通过绑定关系关联。家长不是课时所有者，不拥有孩子的课时，也不能因绑定关系将孩子的课时转移、合并或跨机构使用。

家长绑定关系包括关系称谓、是否主要监护人、绑定状态、核验状态、核验来源、核验时间和修订信息。一个学员可以有多个有效家长绑定，但同一时刻最多一个有效主要监护人绑定。

绑定关系可以授予家长后续的查询和获准操作范围，但不能改变“学员＋机构”课时账户的所有权。解绑只影响访问和关系状态，不自动删除、转移或恢复任何课时。

### 2.5 教师

教师是人员档案和潜在操作主体。教师档案当前可以包含姓名、账号关联、电话、职称、头像、简介、教育经历、教学经历、教学风格、教学成果、教学年限、学生数量、续费率、教学理念、图片、特长、置顶和试听顾问等旧系统字段。

教师不是课时所有者，也不是机构课时边界。教师与机构存在任职或服务关系；教师未来可以被授权操作分配给自己的课次，但在当前 P4 中，教师档案级课次工作域尚未开放。

### 2.6 课时包、课时批次和课时账户

课时包是机构提供课时的一种发放模板或说明，不是课程、班级、教师、校区或教室的绑定容器。当前课时包模板包含名称、说明、基础课时、赠送课时、状态和修订号。

课时包必须归属一个机构。课时包归属机构是为了确定服务提供方和可使用边界，不是为了限定学员未来必须参加某门课程、某位教师或某个场地。

课时包修改通过修订和不可变版本表达。已经发放的批次保存模板名称、版本、基础课时、赠课等快照；以后修改模板不会改写已经发生的发放含义。

课时账户按“学员＋机构”唯一建立：

```text
学生 S + 机构 I = 机构 I 下的一本课时账
```

账户余额只能在统一课时账本服务中变化。没有课时余额的学员可以暂时没有账户记录；发生发放或消费时由账本服务按事务规则创建或锁定账户。

## 3. 核心业务判断

### 3.1 课时是稳定的基础权益

课时是学员从某机构获得的可消费权益。课时的来源可以是线下购课登记、赠送、补课、迁移期初或人工调整，但系统只记录课时业务事实，不推导或伪造支付事实。

课时包的最大自由度表现为：购买或发放后，课时不被课程、班级、教师、校区、教室等教学资源限定。只要消费发生在同一机构服务边界内，课时可以被该机构的不同教学服务事件消费。

这并不表示课时可以被无规则扣减。每次扣减必须有明确正整数数量、操作人、原因、来源引用和可追溯流水；如果经营上需要小班、一对一或不同合作方采用不同消耗量，应在消费动作中明确记录实际数量，不能临时修改余额或无记录扣课。

### 3.2 机构是课时服务边界

课时账户、课时批次、课时流水、课次和课次名单中的机构必须相互一致。机构 A 的课时不能因为学员同时服务于机构 B 而自动借给机构 B；组织级统计余额不能被展示或当作跨机构可消费余额。

课次消费机构由课次的 `institutionId` 决定。消费时，系统必须同时确认：

1. 机构存在且处于可服务状态；
2. 学员处于该机构的有效服务关系；
3. 消费使用该学员在该机构的账户；
4. 课时流水、批次分摊和课次名单都记录同一机构。

### 3.3 课次是消费载体，不是课时所有权

课次表示一次教学服务事件，是签到和消课的载体。课次可以独立创建，不要求先有课程、班级、排课、教师、校区或教室。

当前课次字段包括名称、开始时间、结束时间、来源、默认消耗课时、备注、状态、生命周期时间戳和修订号。课程、班级、教师、校区、教室等后续可以作为可选关联或课次生成来源，但这些关联不能反向改变已经发生的签到、消课、批次分摊或历史快照。

课次默认课时只是操作建议值，实际消课请求仍必须给出明确数量。默认值不能绕过正整数校验，也不能在历史消课后重新计算过去的扣减。

## 4. 组织、机构与人员关系规则

### 4.1 关系结构

```text
组织（单实例技术租户）
├── 机构（自营或合作教学服务方）
│   ├── 课时包模板与版本
│   ├── 学员服务关系
│   ├── 课时账户与批次
│   └── 课次、名单、签到与消课
├── 学员（组织级档案）
│   └── 家长绑定关系
└── 教师（组织级档案）
    └── 机构任职／服务关系
```

### 4.2 学员与机构关系

- 学员档案只维护一份，机构通过关系表获得服务范围。
- 只有有效的学员－机构关系才能加入该机构课次名单或产生该机构课时账户。
- 关系停用不删除历史课时和历史课次事实。
- 机构管理员只能访问当前机构被授权的学员字段；不能仅凭提交一个机构 ID 取得额外数据范围。
- 同一学员可以与多个机构建立关系，但每个机构的账本和服务事实必须独立。

### 4.3 家长绑定关系

- 家长绑定是访问和监护关系，不是课时账户。
- 绑定状态、核验状态和撤销状态必须被保留，以支持审计和后续家长端访问控制。
- 同一手机号、姓名或其他联系方式不能在没有核验规则的情况下自动认领学员。
- 家长后续只能访问自己有效绑定的学员；不能因绑定一个学员而读取同机构其他学员名单。
- 家长读取课时和签到属于后续档案级授权工作，当前 P4 管理端不将家长视为可操作课次的机构管理员。

### 4.4 教师与机构关系

- 教师可以服务多个机构，机构关系分别维护。
- 教师账号、教师档案和机构任职关系是三个不同事实，不能仅因有教师档案就自动获得课次操作权限。
- 后续教师工作域必须以机构关系、课次分配和能力配置共同决定范围。
- 教师工作域不能扩大为“机构内所有学员、所有课次、所有课时流水”。

## 5. 课时账本规则

### 5.1 账本对象

课时账本由四类事实组成：

1. **账户（Account）**：学员在某机构的当前余额投影、累计入账、累计扣减、最后序号和修订号。
2. **批次（Batch）**：每次发放产生的独立来源和剩余量。
3. **流水（Movement）**：每次增减课时的不可变凭证。
4. **批次分摊（Allocation）**：一笔扣减具体消耗了哪些批次、各批次多少课时。

账户是查询投影，流水是审计事实，批次是消费分摊事实。三者必须在同一事务中保持守恒。

### 5.2 发放规则

发放可以使用机构课时包的当前有效版本，也可以使用自定义课时数。发放请求必须包含：

- 学员和机构；
- 来源类型；
- 基础课时和可选赠送课时，或明确的课时包模板；
- 原因；
- 可选来源引用；
- 操作人和幂等键；
- 账户期望修订号。

发放数量为基础课时加赠送课时，必须是正整数。每次成功发放创建新批次和对应 `grant` 或调整流水，不覆盖旧批次，不直接设置账户余额。

来源引用在可重复业务中应保持稳定，以便数据库唯一约束和幂等机制阻止重复发放。重复请求在相同幂等键和相同载荷下应安全返回原结果；相同幂等键但载荷不同必须报冲突。

### 5.3 FIFO 消费规则

同一学员、同一机构账户内，消费默认按照批次发放时间和批次 ID 的稳定顺序 FIFO 分摊：

```text
先按 grantedAt 升序，再按 batchId 升序
```

消费可以跨多个可用批次，但不跨机构。系统自动完成分摊，调用方不需要手动选择课时包。

成功扣减必须同时：

- 锁定账户和参与分摊的可用批次；
- 校验账户版本和余额；
- 更新批次已消费量、剩余量和状态；
- 更新账户余额、累计扣减和序号；
- 写入 `consume` 流水；
- 写入每个批次的分摊记录；
- 写入业务审计和 Outbox 事件。

### 5.4 余额守恒

账户必须满足：

```text
balanceUnits = lifetimeCreditedUnits - lifetimeDebitedUnits
```

每个批次必须满足：

```text
totalUnits = consumedUnits + withdrawnUnits + remainingUnits
```

批次状态规则：

- `available`：剩余量大于 0；
- `depleted`：剩余量为 0，已经消费完；
- `reversed`：剩余量为 0，整批发放被撤销，不能再消费。

数据库检查约束、应用服务校验和事务锁共同保证余额不得为负。不得通过直接修改账户余额、删除流水或删除批次来“对平”账本。

### 5.5 不可变流水和纠错

普通业务 API 不得更新或删除已经入账的课时流水。不同错误类型使用不同操作：

- 发放未被使用：可以执行整批 `grant_reversal`，原批次进入 `reversed`；
- 发放已部分消费或扣回：不能整批撤销，必须使用明确的剩余量扣回或人工调整流程；
- 已发生消费：使用 `consume_reversal` 冲正原消费；
- 线下退款：如果业务需要，只记录授权的课时扣回，不记录或伪造退款金额；
- 规则变化：只影响未来操作，不重算历史流水。

所有冲正必须引用原流水。消费冲正按原消费流水的分摊记录逐批恢复原批次，不新造来源不明的课时。一个消费最多只能有一笔对应冲正；冲正后如果要重新消费，必须创建新的消费操作号和新的消费流水。

## 6. 课次状态机

### 6.1 课次状态

```text
draft ──open──> completed
  │              ▲
  └──cancel──────┘
open ──cancel──> cancelled
```

更准确地说，允许转换为：

- `draft -> open`：打开课次，进入可点名状态；
- `open -> completed`：所有名单记录都已处理，不再有 `pending` 点名；
- `draft -> cancelled`：未开始的课次可取消；
- `open -> cancelled`：进行中的课次可取消，但不能存在有效消课。

已完成或已取消的课次不能重新打开、编辑或取消。当前实现使用课次修订号进行乐观并发控制；客户端提交过期修订号必须刷新后重试。

### 6.2 课次创建与编辑

创建课次必须指定机构、名称、开始时间和结束时间，结束时间必须晚于开始时间，默认消耗课时必须为正整数。创建时机构必须有效且可服务。

草稿和进行中课次可以更新允许字段。已完成或已取消课次不可编辑。后续若要修改已发生课次的教师、地点或其他资源，应通过带修订痕迹的受控更正，不得覆盖导致历史消费失去原始语义。

### 6.3 课次取消

课次取消必须保留取消时间和可选原因。只要课次存在有效 `consumed` 记录，就不能直接取消；必须先逐笔执行消费冲正。`failed` 或已 `reversed` 的记录不代表当前仍有有效扣减，不会阻止取消，但失败原因和冲正事实仍需保留。

## 7. 名单、快照和机构隔离

### 7.1 加入名单

只有当前机构有效学员可以加入当前机构课次。一个学员在同一课次只能有一条名单记录；重复加入返回冲突，不产生第二条签到或消费路径。

名单可以在草稿或进行中状态维护，完成或取消后锁定。当前实现支持批量添加，但每个学员仍按独立关系校验。

### 7.2 姓名快照

加入名单时保存学员姓名快照。快照用于保证历史课次在学员档案改名后仍可读、可审计；它不替代学员 ID，也不改变学员与机构关系。

历史名单、签到和消费不得因为学员后续改名而被重写。详情页如需要展示当前姓名，可以另行显示，但必须保留快照字段作为发生时的业务事实。

### 7.3 数据库级隔离

应用服务在加入名单前会校验学员与机构的有效关系，数据库还使用复合外键同时约束：

- `sessionId + institutionId` 必须指向同一机构的课次；
- `studentId + institutionId` 必须指向同一机构的有效学员服务关系。

因此，不能只通过修改请求中的 `institutionId`，也不能通过绕过 HTTP 层的脚本或其他模块，写入跨机构课次名单。

## 8. 签到与消课分离规则

### 8.1 签到状态

名单记录的签到状态为：

- `pending`：待点名；
- `present`：到课；
- `late`：迟到；
- `leave`：请假；
- `absent`：缺勤。

签到是出勤事实，消费是课时事实，两者必须分开存储和审计。签到状态不能直接等同于扣课成功，扣课成功也不能反向伪造签到。

### 8.2 可消课条件

只有 `present` 或 `late` 可以消课。`pending`、`leave` 和 `absent` 不能消课。

消课请求必须包含：

- 课次和名单记录；
- 正整数课时数量；
- 唯一操作号；
- 可选原因；
- 名单记录期望修订号；
- 当前操作人和机构范围。

课次处于 `open` 或 `completed` 时可以处理消课；草稿和取消状态不可消课。当前策略允许完成后对已点名但尚未消费的记录进行补充处理，实际是否开放给教师应由下一阶段能力权限决定。

### 8.3 消费状态

名单消费状态为：

```text
not_consumed -> consumed -> reversed
      │
      └──────> failed -> consumed（使用新操作号重试）
                           │
                           └──reversed
```

- `not_consumed`：尚未尝试成功消费；
- `consumed`：课时账本已成功扣减，并关联消费流水；
- `failed`：本次尝试因余额不足或批次账本不一致而未扣减，保留错误码、错误消息和操作号；
- `reversed`：原消费已经冲正，原消费流水和冲正流水均保留。

失败不是成功扣课。余额不足时，课时账户和批次不得发生扣减，名单仅记录失败结果，之后可以在补充课时后使用新的操作号重试。除余额不足和批次余额不一致这类可安全记录的业务失败外，事务性或系统性错误应整体失败，不能被伪装成普通余额不足。

### 8.4 消费数量

名单上的 `plannedUnits` 是计划数量，成功消费的 `consumedUnits` 是实际数量。实际数量可以按课次默认值填写，也可以根据服务类型、班型或合作机构规则由授权操作人明确调整，但必须在消费操作中落库，不能从后来修改的课程、教师或场地关联重新推导。

第一版统一使用正整数课时。若未来需要半课时或其他精度，必须先统一存储精度、舍入规则、余额守恒和迁移规则，不能在不同模块各自解释小数。

## 9. 幂等、并发与可追溯性

### 9.1 幂等

课时发放、课时调整、课时扣回、课时冲正、课次消课和消费冲正都必须使用幂等请求机制。对于相同操作号：

- 相同业务范围和相同载荷：安全返回原结果，不重复记账；
- 相同操作号但载荷不同：返回冲突，不能静默采用新载荷；
- 不同操作号：视为新业务操作，但仍受当前状态和唯一业务约束限制。

批量消课使用批量操作号作为请求身份，同时每条名单记录仍必须形成可追踪的单项结果。批量接口不能因为其中一条余额不足，就把其他已经成功的记录伪装成全部成功或全部失败；返回结果必须区分每条记录状态。

### 9.2 乐观并发和事务锁

课次、名单记录、课时账户和批次均使用修订号或数据库行锁保护。任何写入必须带期望修订号；版本冲突时返回 409 类错误，要求调用方重新读取。

消课事务的基本锁定范围是课次、名单记录、课时账户以及将要分摊的批次。课时账本和名单状态必须在同一事务中提交，避免出现“名单显示已消费但账户未扣减”或“账户已经扣减但名单仍显示未消费”。

### 9.3 审计与 Outbox

以下操作必须留下业务审计：创建和修改课次、状态转换、加入名单、签到、成功消费、消费失败、消费冲正、课时发放、调整、扣回和发放冲正。

成功的课时账本变化还要产生 Outbox 事件。审计、流水、批次分摊、账户投影和 Outbox 必须在同一事务内提交；事务回滚时不能留下孤立的成功通知或孤立流水。

审计至少要能回答：谁在什么时间、对哪个组织／机构／学员／课次／名单做了什么操作，变化前后是什么，使用了多少课时，关联了哪一笔流水，失败或冲正原因是什么。

## 10. 当前访问控制边界

### 10.1 当前已经开放

当前 P4 管理端课次工作台主要面向机构数据范围：平台管理员和机构管理员可以在授权机构范围内执行课次、名单、签到和消课操作。服务层仍会再次校验机构范围，不把 HTTP 路由上的机构参数视为权限本身。

当前机构范围要求：

- 查询课次必须属于当前机构范围；
- 查询名单必须属于当前课次和机构；
- 加入名单必须是当前机构有效学员；
- 消课只能扣减当前机构的学员账户；
- 课时账户的变更写操作当前只允许机构范围；
- 教师和家长范围当前不能直接调用机构级课次工作台。

### 10.2 当前尚未开放

以下能力虽然已经在访问控制模型中预留角色或能力概念，但不应被误认为 P4 已完成：

- 教师按本人被分配课次查看和点名；
- 教师批量点名移动工作台；
- 教师是否可以执行消课，以及可执行的课时上限或能力；
- 家长按有效绑定查看孩子的课次、签到和机构课时；
- 家长查看其他同课次学员；
- 通知、补签审批、导出和档案级历史查询。

## 11. 下一阶段教师工作域规则

教师端采用微信小程序作为移动操作入口，不在本阶段额外建设同等功能的 Web 教师界面。小程序只是交互载体，所有机构隔离、权限、幂等、事务和账本规则仍由服务端统一执行。

下一阶段建议按以下边界实现：

1. 教师只能看到与其有效机构关系和已分配的课次；不能通过修改查询参数读取机构全部课次。
2. 教师默认能力是查看课次名单和记录签到；批量点名只是多个独立签到事实的便捷提交，不改变逐条审计和修订规则。
3. 教师是否可以执行消课必须通过显式 `setLessonUnits` 能力授权；没有该能力时只能完成签到，不能直接改变课时账户。
4. 教师批量操作必须支持部分结果反馈、重复提交安全重试、版本冲突提示和离线／弱网下的失败重试策略。
5. 教师不能查看、修改或选择课时批次；课时 FIFO、余额校验和原批次冲正始终由服务端课时账本决定。
6. 教师只能访问被分配课次的名单；不能因为是某机构教师而读取该机构全部学生、家长联系方式或全部流水。
7. 家长工作域另行按学生绑定关系设计，默认只读，并严格限制到自己有效绑定的学员。

教师工作域仍然要复用当前课次、名单、签到和消费 Contract，不应在小程序中复制一套业务规则或直接访问数据库。

## 12. 明确不属于本阶段的内容

以下事项不属于当前 P4 业务闭环，也不应成为课时和签到消课上线的前置条件：

- 财务收款、退款金额、支付订单、资金账户；
- 合作机构分成、代收结算、佣金、对账和财务报表；
- 多租户 SaaS 开通、租户切换、跨组织共享数据库；
- 周期卡、按时间段权益、自动续费或周期权益折算；
- 课程、班级、报名、复杂排课和固定课表；
- 教室、校区、教师对课时包的强绑定或消费限制；
- 跨机构转课、家庭共享课时、机构间余额互通；
- 可视化任意规则脚本或允许关闭核心数据完整性约束的规则引擎。

线下业务可以自行完成收款和合作方分配。系统如需记录，只能记录发课来源、服务机构、课时数量和操作原因等运营事实，不能用“已录入发课”代替“已支付”，也不能把线下分账状态伪造为系统财务事实。

## 13. 后续扩展原则

### 13.1 资源关联是可选的

课程、班级、教师、校区、教室和排课可以为课次提供默认信息、查询维度或冲突检查，但它们不是课时所有权，也不是课时消费资格。

资源关联被修改、停用或删除时，不得删除或重写已经发生的课次、签到、消费流水、批次分摊和姓名快照。资源只可作为课次事件的上下文，不能成为历史课时事实的替代来源。

### 13.2 规则逐层增加

规则分为三层：

- **不可关闭的核心底线**：机构隔离、账户守恒、非负余额、正整数、幂等、事务、不可变流水和权限范围；
- **集中实现的默认政策**：FIFO 顺序、默认消费数量、可消费签到状态、完成条件和冲正要求；
- **后续可配置的经营政策**：请假是否扣课、缺席是否扣课、取消窗口、补签审批、有效期和特殊消耗数量。

经营政策必须保存实际执行结果和规则版本。规则改变只影响未来业务，不自动重算历史事实。任何配置都不得关闭核心底线。

### 13.3 迁移原则

旧系统数据迁移时，无法证明机构归属、学员归属、课时来源或历史扣减链路的记录不得静默猜测。应进入迁移例外清单，经过确认后采用可追溯的期初发放或保留为只读历史证据。

迁移产生的普通课时必须按“学员＋机构”建立账户和批次，保存旧合同、订单、课程或课包标识作为来源元数据，但不能把旧课程或订单强行变成新系统课时消费前置条件。周期卡和无法映射为普通课时的权益继续后置处理。

## 14. 当前实现核对结论

本规则文档与当前 P4 代码的关键对应关系如下：

| 业务规则                         | 当前实现依据                                                                 |
| -------------------------------- | ---------------------------------------------------------------------------- |
| 课时账户按学员＋机构隔离         | `lesson_accounts` 唯一约束及 `LessonAccountsService` 机构、学员校验          |
| 课时包只归属机构，不绑定课程资源 | `lessonPackageTemplates` 与 `lessonPackageVersions` 仅表达机构和课时模板快照 |
| 批次和流水不可随意覆盖           | `lesson_batches`、`lesson_movements`、分摊表及账本服务写入路径               |
| FIFO 消费                        | 可用批次按 `grantedAt`、`id` 升序锁定和分摊                                  |
| 余额守恒和批次守恒               | 数据库 check 约束、账户修订和账本事务                                        |
| 课次状态机                       | `LessonSessionsService` 的 open、complete、cancel 和数据库生命周期约束       |
| 名单姓名快照                     | `teaching_session_attendances.studentNameSnapshot`                           |
| 机构级名单隔离                   | 复合外键同时检查课次机构和学员机构                                           |
| 签到与消费分离                   | `attendanceStatus` 与 `consumptionStatus` 两套字段和独立服务操作             |
| 余额不足不扣减                   | 账本业务错误被记录为 `failed`，账户和批次不产生扣减                          |
| 消费冲正原路恢复                 | `reverseConsumptionInTransaction` 按原流水 allocation 恢复原批次             |
| 幂等和审计                       | Idempotency 服务、业务审计和课时 Outbox 事务写入                             |
| 当前访问边界                     | 课次服务的 institution scope 校验；教师、家长档案级工作域待后续实现          |

当前 P4 已形成管理员／机构管理员可用的课次、签到和消课闭环；教师微信小程序工作台、教师档案级授权、家长只读访问和旧系统历史课次迁移属于下一阶段或后续迁移工作，不应在验收时被视为已经完成。
