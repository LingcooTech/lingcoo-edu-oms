# 订单退款与权益回收业务规则

## 1. 目标与边界

订单退款不是一个孤立的支付动作，而是“原订单、原支付、原权益”三者一致地反向处理。本阶段支持：

- 已完成课时包订单的全额退款；
- 已完成周期卡订单的全额退款；
- 线上订单按原支付交易退款；
- 线下订单由操作员确认已退回款项后，在系统中完成退款登记；
- 对应课时或周期卡权益自动回收；
- 全流程保留订单状态、支付退款记录、课时流水和审计记录。

本阶段不支持部分退款，也不自动处理已经发生消费的订单权益。涉及已消课、已使用周期卡、违约金或协商退款的情况，需要先人工核算，后续再建设独立的复杂退款申请流程。

## 2. 可退款条件

只有状态为 `completed` 的订单可以首次发起退款。系统按商品类型执行不同校验：

### 2.1 课时包

退款必须定位到该订单发放形成的原始课时流水和原始批次，并同时满足：

- 批次状态仍为可用；
- 已消费课时为 0；
- 已扣回课时为 0；
- 剩余课时等于该批次发放总课时。

因此，系统回收的是“该订单产生的完整权益”，不会从其他课时批次凑数，也不会因学员账户总余额足够就错误退款。

### 2.2 周期卡

周期卡权益必须从未使用，即 `usedQuantity = 0`。满足条件时，将订单对应权益置为已撤销。只要已经产生使用记录，就不允许通过本流程自动退款。

## 3. 状态流转

```text
completed（已完成）
    │ 发起退款并通过版本校验
    ▼
refunding（退款处理中）
    │ 回收订单权益
    │ 线上：原支付交易退款成功
    │ 线下：操作员确认款项已退回
    ▼
refunded（已退款）
```

订单先进入 `refunding`，再执行权益回收和资金退款。若微信返回“处理中”或支付结果暂时无法确认，订单保留在 `refunding`，后台显示“继续退款”，使用同一退款请求键查询原退款结果，不会创建第二笔退款。

## 4. 课时账本处理

课时退款不删除原发放流水，也不直接改写历史余额。系统新增一笔：

- 类型：`grant_reversal`；
- 方向：`debit`；
- 数量：原订单批次的全部课时；
- 原批次状态：`reversed`；
- 原批次剩余课时：0。

这样可以同时看到“订单曾经发放过什么”和“为什么被完整回收”，满足业务追溯和审计要求。

账户与批次在数据库事务中加锁。退款和签到消课并发发生时，只有先满足规则并获得锁的一方能够成功，避免超扣、重复回收或退款后继续消费。

## 5. 支付处理

### 5.1 线上订单

- 必须关联原支付意图；
- 固定使用订单维度的退款请求键；
- 固定执行订单全额退款；
- 微信退款请求使用系统退款记录 ID 作为 `out_refund_no`；
- 微信返回 `PROCESSING` 时，后续通过同一个 `out_refund_no` 查询，不重复发起；
- 微信明确成功后，订单才进入 `refunded`。

### 5.2 线下订单

系统不能代替线下转账或现金交付。操作员点击“确认已线下退款”，代表已经按原付款方式把款项退回客户；系统随后登记订单退款并回收权益。退款原因必须填写并进入审计记录。

## 6. 幂等、并发与审计

- 订单使用状态和 revision 做乐观并发控制；
- 课时回收使用订单号生成稳定幂等键；
- 支付退款使用订单 ID 生成稳定请求键；
- 重复调用已退款订单直接返回原结果；
- 退款处理中订单可以继续核验原退款；
- 课时发放、课时回收、周期卡撤销、支付退款各自保留独立事实；
- 审计记录包含退款开始、退款完成、退款原因、订单号、渠道和金额。

通用支付退款接口仍禁止直接退款购课订单。购课退款必须进入订单专用流程，防止出现“钱退了但权益没回收”的旁路操作。

## 7. 暂不自动处理的情况

- 已经消费部分或全部课时；
- 已经使用周期卡；
- 部分退款、手续费、违约金、优惠分摊；
- 跨订单抵扣或把权益转给其他学员；
- 试听占位费的自动退款；
- 需要审批、多角色复核或财务结算的退款。

这些场景后续应建设独立退款申请/退款单聚合，明确审批、金额核算、权益调整方案和对账状态，不能放宽当前全额未使用退款规则来兼容。
