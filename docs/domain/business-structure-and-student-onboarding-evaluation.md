# 业务结构与学员入学流程评估结论

**评估日期：** 2026-09-09
**工作方式：** 先只读评估代码、Contract、API、数据库模型和管理端交互，再按确认结论实施
**适用项目：** `lingcoo-edu-oms`
**实施状态：** 评估结论已于 2026-09-09 完成首轮落地；本文同时保留设计依据和实施结果

## 1. 评估结论摘要

OMS 的课时账本底层方向保持不变。本轮已经把“学员建档—课时账户—课时发放—教学安排”接成可中断、可继续的后台引导流程。

当前真实实现已经调整为：

```text
新建学员或新增机构服务关系
  → 在同一事务中创建零余额课时账户
  → 可立即发放课时或进入教学安排
```

原有“第一次课时变更时懒创建账户”的能力仍作为历史数据兼容保护，但不再是新建学员的正常流程。

当前流程为：

```text
建立学员与机构服务关系
  → 自动创建该机构下的零余额课时账户
  → 引导发放课时
  → 引导安排教学服务
```

本次评估也确认，后台菜单不应继续简单沿用“教学资源—教务管理—运营管理”的历史分组，而应明确区分：

1. 组织与供给；
2. 学员与关系；
3. 课时与交易；
4. 教学交付；
5. 招生转化；
6. 系统治理。

## 2. 当前实现核查

### 2.1 新建学员当前做了什么

新建学员 API 是：

```text
POST /api/institutions/:institutionId/students
```

服务端现在在一个事务中完成：

1. 校验机构处于有效状态；
2. 写入 `people_students` 学员档案；
3. 写入 `people_student_institutions` 学员—机构服务关系；
4. 创建 `(studentId, institutionId)` 唯一的零余额课时账户；
5. 写入账户创建和学员创建审计事件。

任何一步失败都会回滚档案、服务关系和账户，避免形成半完成状态。对应实现见：

- [PeopleService.createStudent](/Users/admin/Projects/lingcoo-edu-oms/apps/server/src/modules/people/application/people.service.ts:107)
- [PeopleRepository.createStudent](/Users/admin/Projects/lingcoo-edu-oms/apps/server/src/modules/people/infrastructure/persistence/people.repository.ts:142)
- [LessonAccountProvisioningService](/Users/admin/Projects/lingcoo-edu-oms/apps/server/src/modules/lesson-accounts/application/lesson-account-provisioning.service.ts:1)

### 2.2 当前课时账户什么时候创建

课时账户在创建学员或新增机构服务关系时，由课时模块公开的账户供应端口创建，使用 `(studentId, institutionId)` 唯一约束。

课时发放、调整和消课仍调用 `lockOrCreateAccount()`：

- 第一次发放课时；
- 第一次课时调整；
- 第一次消课。

该方法现在主要承担并发锁定和历史数据兼容兜底；它使用 `INSERT ... ON CONFLICT DO NOTHING`，然后锁定账户行，保证并发下不会重复创建账户。对应实现见：

- [LessonAccountsRepository.lockOrCreateAccount](/Users/admin/Projects/lingcoo-edu-oms/apps/server/src/modules/lesson-accounts/infrastructure/persistence/lesson-accounts.repository.ts:50)
- [LessonAccountsService.grant](/Users/admin/Projects/lingcoo-edu-oms/apps/server/src/modules/lesson-accounts/application/lesson-accounts.service.ts:145)

对于本轮实施前已经存在、但从未发生课时变更的历史关系，账户查询仍可能返回 `null`；这类记录应由后续数据修复或迁移补齐，不能伪造成已有余额。

### 2.3 当前后台交互

学员新建成功后，现在会打开结果 Modal，展示：

- 机构服务关系已建立；
- 课时账户已创建；
- 当前账户余额；
- 立即发放课时、查看账户和安排教学入口。

发放成功后显示本次发放量和当前余额；运营人员也可以稍后从独立的课时账户页面处理。对应实现见：

## 3. 推荐的账户业务规则

### 3.1 账户建立规则

推荐将规则明确为：

> 学员加入某个机构的有效服务关系时，自动建立该学员在该机构下的零余额课时账户。

模型关系为：

```text
学员档案 + 机构服务关系 = 该机构课时账户
```

不是：

```text
学员档案 = 一个全局课时账户
```

这样可以确保：

- 同一学员进入多个机构时拥有多个独立账户；
- A 机构和 B 机构的课时永远分开；
- 新学员即使尚未购买课时，也有明确的“余额为 0”账户状态；
- “没有账户”和“有账户但尚未发课”不再混淆；
- 账户是机构服务关系的运营结果，而不是课程档案的附属结果。

### 3.2 发放规则

自动建立零余额账户后，发放课时仍然必须生成：

- 发放批次；
- `grant` 课时流水；
- 来源类型；
- 操作原因；
- 操作账号；
- 幂等键；
- 可选的课时包模板版本快照。

账户自动创建不能等同于已经购买或已经发放课时。账户余额仍必须由课时流水产生。

### 3.3 账户和课时包的边界

课时账户不绑定课程、班级、教师、校区或教室。

课时包可以作为机构提供的通用课时商品，但它的作用是定义发放数量、名称、赠送数量和运营说明，不是决定学员只能上什么课程。

## 4. 供给、需求、交易和交付四层模型

当前业务更适合采用以下四层结构：

```text
供给层 → 交易/权益层 → 需求层 → 教学交付层
```

### 4.1 供给层：组织与教学服务能力

包括：

- 组织；
- 自营机构和合作机构；
- 校区；
- 教室；
- 课程；
- 教师。

其中：

- 组织是系统部署和经营主体；
- 机构是教学服务和课时提供方；
- 校区和教室更适合作为组织级共享的物理供给资源；
- 教师可以与一个或多个机构建立任职关系；
- 课程是机构提供的服务目录；
- 任何供给资源都不能成为普通课时账户的必要条件。

推荐菜单名称为：

> 教学资源

下设：

- 组织设置；
- 机构管理；
- 校区管理；
- 教室管理；
- 课程管理；
- 教师档案。

### 4.2 需求与教学交付层：学员和家长关系

包括：

- 学员档案；
- 家长档案；
- 家长绑定和核验；
- 学员—机构服务关系；
- 学员的课程和教学服务需求。

学员是课时权益主体，家长是访问和代办主体。家长绑定不转移课时所有权。

推荐菜单名称为：

> 教务管理

教务管理同时承载学员需求的组织和教学服务的实际安排，包括：

- 学员档案（含家长绑定）；
- 班级管理；
- 排课计划；
- 课次管理；
- 签到消课。

这里的班级和排课计划不是静态供给资源，而是围绕学员需求形成的教学组织安排。课次是实际交付事件，签到和消课是交付结果。

### 4.3 交易/权益层：课时商品和账本

包括：

- 课时包商品；
- 课时发放；
- 课时账户；
- 课时批次；
- 课时流水；
- 订单；
- 线下收款和收据；
- 线上支付订单；
- 课时经营数据。

课时包可以被视为商品，因此“课时账本”应该是独立的一级业务菜单，不应继续隐藏在宽泛的“运营管理”中。

但必须保持以下关系：

```text
订单/支付事实 → 触发课时发放
课时账户/流水 → 记录实际课时权益
```

订单不是课时账户，支付不是课时流水。赠课、补发、迁移期初等场景可以没有订单，但仍然必须有课时发放流水。

推荐菜单名称为：

> 课时账本

下设：

- 课时商品/课时包；
- 课时账户；
- 课时流水；
- 订单与收款；
- 课时经营数据。

当前阶段可以先实现课时商品、账户和流水；订单、收款、收据及财务数据后续接入，但不能反向破坏账本边界。

### 4.4 供给与需求的关系

教学资源负责提供可用的服务能力，教务管理负责把学员需求与这些能力进行匹配和安排：

```text
教学资源：机构、校区、教室、课程、教师
                    ↓ 匹配与组织
教务管理：学员、班级、排课计划、课次、签到消课
```

资源可以变化，历史课时和历史交付事实不能被重写。资源缺失时，仍然可以创建独立课次并执行基础签到消课。

## 5. 推荐的学员入学流程

### 5.1 目标流程

```text
选择服务机构
  ↓
创建学员档案
  ↓
绑定/登记家长
  ↓
建立机构服务关系
  ↓
自动创建零余额课时账户
  ↓
发放课时
  ↓
安排教师、校区、教室和班级
  ↓
制定排课计划并生成课次
  ↓
签到消课
```

### 5.2 新建学员后的交互

新建学员完成后，不能只显示“学员已创建”。建议显示结果 Modal：

```text
学员档案已创建
服务机构：某某机构
课时账户：已创建
当前余额：0 课时
```

提供三个操作：

1. **立即发放课时**：打开课时发放 Modal；
2. **安排教学**：进入教学安排流程；
3. **稍后处理**：返回学员列表。

### 5.3 发放课时后的交互

发放成功后显示：

```text
课时账户已更新
本次发放：20 课时
当前余额：20 课时
发放批次：已生成
课时流水：已生成
```

提供后续操作：

- 去安排教学；
- 查看课时账户；
- 返回学员档案。

### 5.4 不应做成强制大事务

前端可以把上述步骤设计成连续引导流程，但后端不应把以下所有事项强制合并为一个不可拆分的大事务：

```text
新建学员 + 发课 + 分配教师 + 分配教室 + 创建班级 + 排课 + 创建课次
```

原因是：

- 学员可能先建档，暂时没有购买课时；
- 学员可能已经有课时，但还没有确定课程和时间；
- 教师、教室或班级可能尚未配置；
- 课时账户可以独立运行，不依赖教学资源；
- 学员可能只购买课时，尚未安排具体服务。

因此应采用：

```text
后端：多个独立业务用例
前端：连续的引导式流程
```

这里的“前端”不只指小程序，也包括管理后台。后台同样可以提供一套快捷操作的完整流程，但快捷流程不能绕过任何标准业务用例、权限校验、事务、幂等和审计规则。

### 5.5 后台快捷流程的正确定位

后台应同时提供两类入口：

#### 独立业务用例入口

用于日常维护、补录、纠错和专业操作，例如：

- 单独新建或编辑学员；
- 单独查看或调整课时账户；
- 单独发放、扣回或冲正课时；
- 单独维护教师、教室、课程和班级；
- 单独创建课次或修改签到。

这些入口适合有经验的运营人员，也适合处理历史数据和异常情况。

#### 快捷流程入口

用于高频操作，例如“新建学员并发放课时”“新学员安排首课”“从学员档案进入排课”。快捷流程可以连续打开多个 Modal 或步骤页面，但每一步仍调用对应的标准 Application 用例。

快捷流程可以由应用层编排：

```text
StudentOnboardingWorkflow
  ├─ CreateStudent
  ├─ BindGuardian（可选）
  ├─ EnsureStudentInstitutionLessonAccount
  ├─ GrantLessonUnits（可选）
  └─ OpenTeachingArrangement（可选）
```

它不是一个绕过模块边界的超级接口，也不是把所有步骤强行放进一个数据库事务。每个步骤应返回明确结果，允许中断和继续；只有同一步骤内部需要原子性的事实才放在同一个事务中。

推荐后台交互：

1. 新建学员后展示账户创建结果；
2. 点击“立即发放课时”进入标准发放用例；
3. 发放完成后展示批次、流水和余额；
4. 点击“安排教学”进入标准教学安排用例；
5. 任意步骤可以“稍后处理”，回到学员档案继续。

这样既保留模块化和可测试性，又避免后台人员在多个菜单之间反复寻找学员和账户。

   - 班级管理；

   - 课次管理；
   - 签到消课。
5. **课时账本**

   - 课时账户；

   - 订单与收款；

6. **小程序设置**（后续建设）。

日常高频操作应突出：

- 添加学员；
- 发放课时；

- 排课；

教学资源维护属于低频操作，应作为供给层的基础配置，不应压过课时、学员和教学交付入口。

## 7. 需要特别保持的领域边界

### 7.1 课时账户边界

- 账户唯一归属是“学员 + 机构”；
- 账户不能跨机构消费；
- 余额不能被课程、班级、教师、校区或教室限制；
- 账户余额只能由明确的课时流水产生；
- 不能使用通用余额 PATCH；
- 更正必须使用调整、扣回或冲正流水。

### 7.2 订单和财务边界

- 订单、支付、收据、退款和分成属于交易/财务域；
- 课时发放属于权益域；
- 支付成功可以触发发放，但支付本身不是发放；
- 退款是否扣回课时必须通过明确政策和可追溯操作处理；
- 不允许订单或支付接口直接修改课时账户余额。

### 7.3 教学资源边界

- 教学资源可以为课次提供默认值和上下文；
- 排课可以生成课次；
- 班级可以提供默认名单；
- 资源变化不能改写历史课时流水；
- 资源缺失时仍然可以建立独立课次并完成基础消课。

### 7.4 模块边界

前端可以提供跨模块的连续流程，但后端不能通过共享 Repository 或直接访问其他模块 schema 来实现流程。

推荐使用：

- 学员模块负责学员和机构服务关系；
- 课时模块负责账户、批次和流水；
- 教学交付模块负责班级、排课、课次和签到；
- 应用层编排跨模块用例；
- 通过公开端口、Contract 和事务执行器协作。

## 8. 实施优先级与当前状态

### 第一步：账户生命周期明确化（已完成）

- 在建立有效学员—机构服务关系时创建零余额账户；
- 明确返回账户状态和余额；
- 区分“账户不存在”和“账户余额为零”；
- 保留现有唯一约束和账本守恒规则。

### 第二步：打通学员建档后的发课流程（已完成首轮）

- 新建学员成功结果 Modal；
- 立即发放课时入口；
- 发放后显示账户、批次和流水结论；
- 提供“去安排教学”入口。

### 第三步：调整后台信息架构（已完成首轮）

- 按“业务概览 → 教学资源 → 招生转化 → 教务管理 → 课时账本 → 小程序设置 → 系统设置”调整菜单；
- 将组织、机构、校区、教室、课程和教师统一归入“教学资源”；
- 将学员、家长、班级、排课、课次和签到消课统一归入“教务管理”；
- 将课时商品、账户、流水、订单和经营数据统一归入“课时账本”；
- 为高频业务增加快捷操作入口，但仍调用标准独立业务用例；
- 保留现有路由兼容性，先调整导航和入口。

### 第四步：建设教学安排流程（下一轮）

- 学员选择或确认机构服务关系；
- 匹配教师、校区和教室；
- 创建或加入班级；
- 生成排课计划和课次；
- 课次进入签到消课。

### 第五步：后续接入订单和收款

- 课时包商品化；
- 线下收款和收据；
- 线上订单和支付状态；
- 支付/收款确认后的课时发放；
- 退款、扣回和财务数据规则。

## 9. 最终判断

本次提出的业务梳理比当前后台的菜单和操作流程更加合理，尤其是以下判断应作为后续设计基线：

1. 新建学员后应明确存在该机构的零余额课时账户；
2. 课时包、课时账户、课时流水和订单需要独立的“课时与交易”业务域；
3. 校区、教室、课程、教师属于供给层；
4. 班级和排课计划属于教学组织与安排，不是静态资源；
5. 学员建档、发放课时和教学安排应形成连续操作流程；
6. 前端流程可以连续，后端领域模型仍必须保持模块和事务边界；
7. 课时—消课仍然是整个系统最底层、最稳定的核心闭环。
