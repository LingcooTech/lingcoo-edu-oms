# 核心课时业务规则基线

**文档状态：** 已确认，作为后续模块、API、数据库和迁移实现的领域规则基线
**适用项目：** `lingcoo-edu-oms`
**确认范围：** 单组织、自部署的教培运营管理系统；不包含财务、分成结算和周期卡

## 1. 业务定位

系统服务的是一个自部署的经营组织。组织在技术上是本部署的租户，但本版本不建设多租户 SaaS 的租户开通、租户切换和共享数据库运营能力。

组织可以自己提供教学服务，也可以邀请多个合作机构使用闲置教室、成长空间或其他教学资源。机构是实际提供教学服务、发放课时和承接消课的主体。

当前旧系统中的机构全部按合作机构处理；没有事实依据时，不把机构自动推断为自营。将来组织自营教学时，使用同一机构模型增加自营类型即可，不使用“空机构”代表自营。

## 2. 核心商业关系

最底层的经营闭环是：

```text
学员 ──持有──> 某机构的课时账户 ──通过──> 课次/服务事件 ──产生──> 消课流水
  │
  └──家长绑定：访问和代办关系，不转移课时所有权
```

### 2.1 学员是课时权益主体

- 学员是服务和课时权益的实际持有人。
- 家长只是经核验的关联人，可以获得约定的数据查看或代办能力；家长不拥有学员课时，解绑也不改变课时余额。
- 教师负责执行服务和点名，不拥有学员课时。
- 组织负责系统运营；机构负责具体服务和课时边界。

### 2.2 机构是课时边界

- 课时账户的唯一业务归属是“学员 + 机构”。
- 同一学员可以同时接受多个机构服务，各机构账户必须独立展示、独立发放、独立消费、独立核对。
- A 机构的余额不能被 B 机构的课次借用；机构停用、关系解绑或权限撤销，不自动清零、不自动转移已有余额。
- 机构可以是合作机构，也可以是组织自营机构。机构类型影响运营归属和权限，不改变课时账本的基本结构。

## 3. 课时包和课时账户

### 3.1 课时包保持通用

课时包是机构向学员发放课时的产品模板或业务说明，不是课程合同，也不是排课规则。课时包不强制绑定以下对象：

- 课程或课程系列；
- 班级；
- 教师；
- 校区或教室；
- 课次；
- 订单、支付金额或分成结算。

课时包可以保留名称、说明、默认课时数、机构、版本和来源等信息，方便运营识别；这些信息不得变成消费前置条件。模板修改产生新版本，不改写已经发放的历史批次。

### 3.2 账户、批次、流水三层模型

- **课时账户：** 学员在某机构下的聚合账户，一个学员在同一机构最多一个有效账户。
- **发放批次：** 每次购课登记、赠送、补发、迁移期初或其他获批准的发放形成独立批次。
- **课时流水：** 发放、消费、冲正、扣回和调整都是不可变业务事实。余额是流水和批次的可验证结果，不提供任意修改余额的通用入口。

任何影响余额的命令都必须具备操作者、原因、来源引用、幂等键和必要的修订号/并发校验。重复请求只能得到同一业务结果，不能重复发放或重复消费。

### 3.3 机构服务内可用

课时包必须绑定一个提供课时服务的机构。买到的课时只能在该机构的服务范围内消费；这不是课程限制，而是机构服务边界。

不做在线财务，但系统仍记录运营事实：谁为哪个学员、哪个机构登记了多少课时、何时登记、依据是什么。金额、支付、退款和机构间分成不进入本阶段核心账本。

## 4. 课次、签到和消课

### 4.1 课次是消费载体，不是权益归属

课次表示一次具体的教学服务事件。它必须明确服务机构、时间/状态和操作范围，但课程、班级、教师、校区、教室都是可选关联。

因此以下场景都必须合法：

- 只有机构、学员、时间和课时数，也可以创建独立课次；
- 后续再补充课程、教师或场地，不改变课时账户；
- 更换教师、教室、课程或班级，不迁移、不重建、不改变历史课时；
- 共享教室可以服务不同机构，教室归属不推导扣课机构；
- 排课计划只是生成课次的工具，不是另一套课时系统。

### 4.2 签到和消课分离

- 签到记录“学员是否参加了这次服务”；
- 消课记录“这次服务从哪个机构账户消费了多少课时”；
- 点名成功不等于消课成功；余额不足、待核对或政策不允许时，可以保留签到事实而不伪造扣课成功；
- 同一学员同一天可以参加多个合法课次，不能按“学员 + 日期”粗略去重；唯一识别至少包含课次和名单身份。

默认规则是到课/迟到可以消费，待点名、请假通常不消费，缺席是否消费由后续明确的经营政策决定。每次消费必须明确数量；数量可以按服务事件配置，但不能临时、无原因、无流水地随意扣减。

### 4.3 消费必须可追溯

一次消费至少需要保留：机构、学员、课次/服务事件、签到状态、消费数量、实际分摊批次、操作账号、操作时间、幂等键、来源和结果。

消费按确定的批次分摊策略执行，不能出现负余额。撤销或改数量不修改旧流水，而是以新流水恢复原机构、原批次的事实；同一消费凭证不能重复冲正。

课次完成或取消后，普通编辑不能偷偷重写已经发生的签到和账本事实。历史纠错必须走显式、更正、冲正或人工核对流程，并留下审计记录。

## 5. 权限和模块边界

- 组织管理员可以在授权组织范围内管理运营数据。
- 机构管理员只能访问被授权机构范围；请求中的机构 ID 不是权限本身，服务端必须重新解析数据范围。
- 教师只有在具备账号、教师档案、有效机构任职关系和明确课次分配后，才能访问本人课次和执行被授权的点名能力。
- 家长只有在绑定关系有效且经过核验后，才能访问被绑定学员范围；家长不能因为关联关系获得机构全量数据。
- 教师默认只点名，不直接修改课时账本；能否执行消课必须是显式能力授权。

模块之间不直接访问其他模块的 Repository 或业务 schema。人员、机构、课时账户、课次和资源通过公开端口/Contract 协作；事务由 Application 用例编排，路由只负责协议转换。

## 6. 不属于核心闭环的内容

以下能力可以逐层增加，但不能成为“课时—消课”可运行的前置条件：

- 课程、课程系列、班级、校区、教室、排课；
- 家长端和教师端体验；
- 预约、试听、营销、内容和报表；
- 周期卡、限次卡和有效期复杂政策；
- 收款、退款、分成结算和财务报表。

这些模块可以提供默认值、关联、统计和运营便利，但不能反向限定课时包、课时账户或历史消课事实。

## 7. 迁移和演进原则

1. 先迁移可验证的组织、机构、人员和“学员 + 机构”关系，再迁移普通课时账户、批次和流水。
2. 旧系统的课程、班级、老师、校区和订单字段作为来源证据或上下文，不自动变成目标课时的消费限制。
3. 旧数据归属不明、流水不连续、周期权益、过期有余额和历史关系冲突时，进入异常/隔离清单，不猜测、不静默补平、不跨机构抵消。
4. 正式切换前，旧系统仍可能是发课、扣课、退款扣回和定时任务的写入方；必须先确定停写、增量追平、逐机构核对和恢复方案。
5. 每一次新增规则都必须说明它属于“核心不变量”还是“可配置经营政策”，避免为了方便又把课程、资源或支付重新变成课时前置条件。
