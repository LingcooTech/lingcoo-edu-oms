# 管理后台菜单评估与迁移进度

**更新日期：** 2026-09-09
**适用项目：** `lingcoo-edu-oms`
**目的：** 在不把旧系统耦合结构照搬到新系统的前提下，确定后台菜单顺序，并准确区分“功能工程完成”“运营验收完成”和“生产迁移完成”。

**当前执行策略：** 暂停正式数据迁移，先按旧系统逐模块核对和补齐目标范围功能，再使用全新测试数据完成实际运营演练，最后统一进行数据迁移、对账和切换。详见[旧 Edu 系统功能核对与修订实施方案](../migration/feature-parity-audit-and-revised-sequence.md)。

## 1. 旧系统与实施前 OMS 的差异

旧系统后台主菜单按以下顺序组织：

1. 业务概览：经营看板、数据报表、待办事项；
2. 前台页面；
3. 教学资源：场地、教师、课程；
4. 招生转化：营销、内容、线索、试听；
5. 教务管理：学员、班级、排课点名；
6. 运营管理：订单收款、课时包台账、业务开关、账号、审计；
7. 系统设置：品牌、接口。

实施前 OMS 主菜单是：业务概览、组织与机构、教学资源、教务管理、运营管理、系统设置。原可见项中：教师档案在“教学资源”，学员与家长在“教务管理”，课时包和课时账户在“运营管理”，课次和签到在“教务管理”。本轮实施后的菜单见第 4 节。

旧系统的顺序反映旧产品的历史演进，不应原样复制。尤其是“课程/班级/教师/教室 → 课时包 → 签到”的视觉顺序容易让用户误以为资源决定课时。新 OMS 应让菜单表达已经确认的业务事实：机构和人员先建立边界，课时是核心资产，课次是交付和消费载体，资源只是可选上下文。

## 3. 为什么这样排序

### 3.1 教学资源表达供给能力

组织、机构、校区、教室、课程和教师共同表达教学供给能力，因此放在同一“教学资源”菜单下更容易理解。这里的教学资源是供给方资源，不意味着它们可以限定课时账户。

### 3.2 教务管理表达学员服务安排

学员、家长、班级、排课、课次和签到消课属于围绕学员进行的教学组织和服务交付，不宜拆散到多个一级菜单中。

班级和排课计划不是静态资源，而是将供给能力匹配到学员需求的组织安排。

### 3.3 课时账本应成为显式一级业务域

课时是最稳定的核心资产。课时包、课时账户、课时流水、订单和经营数据共同形成独立的课时商品与权益管理域，因此应使用“课时账本”作为一级菜单名称。

### 3.4 招生转化和系统设置后置

招生转化、小程序设置和系统设置不是当前核心课时—消课闭环的前置条件，可以先保留菜单位置，后续按独立业务域建设。

### 3.5 系统治理不应和日常业务操作混在一起

账号、角色、审计、会话、任务、Outbox、幂等属于系统设置或高级运维能力。普通运营人员主要使用业务概览、教学资源、教务管理和课时账本；管理员再通过系统设置访问治理能力。

## 4. 当前实施结果

本轮已经完成菜单和信息架构首轮调整，没有把独立业务接口合并成超级接口：

1. 已按七个一级菜单的目标顺序重排导航。
2. 已将供给资源、教务安排和课时账本分别归域。
3. 已为校区、教室、课程、班级和课时流水提供独立页面入口；家长绑定只保留在学员详情中，不再提供独立路由。
4. 已增加经营看板快捷入口和独立“快捷操作”页面。
5. 已实现“新建学员 → 展示零余额账户 → 发放课时 / 安排教学”的连续引导。
6. 招生转化、订单收款、课时经营数据和小程序设置以禁用项保留位置，避免造成已经可用的误解。

### 当前总体判断

如果只看“新 OMS 的核心代码和隔离演练”，已经完成 P0–P6 的主要工程骨架；如果看“旧 Edu 功能对照、实际运营和正式迁移”，目前仍处于 **功能补齐与运营验证阶段**，不能称为整体迁移完成。当前不启动正式数据导入。

目前最接近可以进行业务试用的是：

```text
组织/机构/人员 → 机构通用课时 → 独立课次 → 签到消课 → 课时流水核对
```

目前最重要的生产阻塞不是再增加菜单，而是：

1. 处理验证库中“账户存在但所属机构服务已 inactive，导致正常 API 不可见”的 24 课时账户；
2. 补齐教师/家长身份绑定和机构/课次授权，避免页面看得到但真实工作域不可用；
3. 对旧生产数据做最终只读计划和异常签字，明确哪些进入 OMS、哪些留在旧系统归档；
4. 在此之前不启动旧系统停写和正式切换。

## 6. 推荐的下一步

菜单信息架构和首轮核心业务试用前检查已经完成。接下来按功能而不是按数据迁移推进：

1. 先建立旧页面、旧 API、旧字段与 OMS 目标 Contract 的差异清单；
2. 补齐机构、学员、家长、教师及真实授权边界；
3. 用全新测试数据实际演练“建学员 → 发课 → 排课/建课次 → 点名 → 消课 → 查流水 → 纠错”；
4. 再逐项补齐旧系统仍有价值的非核心功能，明确迁移、替代、后置、只读保留或排除；
5. 功能与运营验收通过后，再处理历史异常、正式数据迁移和切换。
